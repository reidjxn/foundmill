# DEPLOY.md — staging on Vercel + Railway + Supabase

What has to be configured outside the repository before foundmill.com runs the real app. Deployment is push-driven (docs/DECISIONS.md "Cloud-first build and deploy"): Vercel builds `apps/web` from `main`; every backend service builds from the root `Dockerfile` with the `APP` variable and runs its package's entry (`node --import tsx src/index.ts` in `apps/<app>`, what `pnpm --filter @foundmill/<app> start` runs) under tini (§3 "Redeploys and shutdown"). Nothing here contains a secret value; the values live in the Vercel and Railway dashboards.

## 1. Merge to `main`

Vercel's production branch is `main`. The cloud build lands on `main-emurwq`; merge it (or ask the session to push) once `pnpm typecheck && pnpm lint && pnpm test` and the Next build are green. Every commit must be authored as `Reid Jackson <40631036+reidjxn@users.noreply.github.com>` or Vercel blocks the deployment (DECISIONS.md "Commit identity").

**Only a green commit deploys.** Until 2026-10-12 nothing enforced the line above: Railway and Vercel deployed every push to `main` while CI ran, and the pushes of 7e5760c, c9dd4bb and 76a112c all shipped with CI red (the unit job and the Playwright job). Three settings close that, all outside the repository:

1. **Railway "Wait for CI", on each of the six app services** (api, gateway, composer, stream, ingest, orchestrator). Railway → project `founder-manager` → the service → Settings → Source → turn on **Wait for CI** (the toggle sits under the connected branch, and appears once the repository has GitHub Actions workflows). With it on, a push to `main` shows as "Waiting for CI" and deploys only after every GitHub Actions run on that commit has passed; if one fails, the deployment is skipped and the running one stays. Through Railway's API it is the service's deployment trigger: `deploymentTriggerUpdate(id: <trigger id>, input: { checkSuites: true })` (read the trigger id with `deploymentTriggers(serviceId, environmentId)`; on 2026-10-11 all six read `checkSuites: false`). Check afterwards: the next push shows "Waiting for CI" on each service.
2. **Branch protection on `main`** (GitHub → reidjxn/foundmill → Settings → Branches → Add rule for `main`): require a pull request, and require the status checks "Typecheck, lint, unit tests", "Playwright (web screens + golden path)", "Banned terms, vocabulary and US English" and "Storybook build" to pass before merging. A red commit then never reaches `main`, which also gates Vercel: Vercel has no wait-for-CI switch for Git deployments, so its production deploy is only as safe as the branch.
3. **Optional on Vercel**: where the project's plan offers Deployment Checks (Project → Settings → Deployment Checks), add the GitHub checks above, so a production deployment is promoted to foundmill.com only once they pass. Not verified from here; branch protection (2) is what the web relies on.

Record a check as green in docs/PROGRESS.md only from the CI run of that commit (`gh run list --branch main`), never from a local run.

## 2. Vercel (`apps/web`)

Project `foundmill` on the Hobby team `fm-2f083c2b` (`team_ekFhICxivRGPOQizeTB5lj0u`), root directory `apps/web`, domains foundmill.com and www.foundmill.com. **One address for sign-in.** foundmill.com is the canonical origin. The app answers every request for www.foundmill.com with a 308 to the same path and query on https://foundmill.com (`redirects()` in `apps/web/next.config.ts`, host-matched, applied before the proxy, so www never sets a cookie). Supabase's PKCE flow keeps the code verifier in a cookie on the host that asked for the magic link, and the api's CORS list is built from `APP_URL`, so sign-in only works when asking for the link, opening it and using the app all happen on one host. The login form therefore always sets the magic link's `emailRedirectTo` to `NEXT_PUBLIC_APP_URL` or, when that is unset, `https://foundmill.com/auth/callback` (development and test without `NEXT_PUBLIC_APP_URL` keep the page's own origin), and `/auth/callback` turns a code it cannot exchange into a notice on `/login` ("Link opened on a different address", "Link expired") above a form that sends a new link (`apps/web/lib/auth/sign-in-errors.ts`). The api also allows the www twin of `APP_URL` (`https://www.foundmill.com`) as a safety net for a page still open on www. Never set the opposite redirect (apex → www) in Vercel: the two would loop. Optionally also set www.foundmill.com to "Redirect to foundmill.com" (308) under Vercel → Project → Settings → Domains; the edge then answers before the app and the result is the same.

**Migrations at boot.** The api applies pending migrations before it listens; no manual `pnpm db:migrate` is needed. The whole run is one transaction that first takes `pg_advisory_xact_lock(7461, 1)` (packages/db `migrator.ts`), so on Supabase's transaction pooler (port 6543) every statement of the run, the lock included, stays on one server connection, and the lock ends with the transaction: on commit, on rollback, and when the process dies (Postgres 14+ notices a dead client within a second even mid-statement). Until 2026-10-11 the api took a session-level `pg_advisory_lock(7461)` and released it with a separate statement; through the pooler the two could land on different server connections, so the lock stayed held by a pooled connection and the next boot waited forever before "api listening". Waiting is bounded: `MIGRATION_LOCK_TIMEOUT_MS` (api, optional, default `60000`) caps the wait for the lock and for any table lock a migration needs; past it the api logs "migration lock not granted within 60 s; exiting with code 1", with the sessions holding the lock (pid, application, start time, query), and exits 1, so Railway restarts it (`restartPolicyType = "ON_FAILURE"`, 5 retries) instead of the deploy hanging. A migration that Postgres aborts to break a deadlock (the previous deployment keeps serving during a redeploy) is treated the same way: "migration aborted by a deadlock with another connection; exiting with code 1", and the restarted boot applies it. Nothing is applied by a run that gives up; a migration that fails rolls back the whole run and the api serves on the old schema (/health still reports the database). Only the api migrates Postgres: composer, gateway, stream, ingest and orchestrator log "database ready" after a read-only probe of the bookkeeping table (they migrate only a PGlite directory they own). `pnpm db:migrate` takes the same lock, so it waits for a booting api and vice versa. To see who holds the lock, in the Supabase SQL editor: `select l.pid, a.application_name, a.state, a.backend_start, a.query from pg_locks l join pg_stat_activity a using (pid) where l.locktype = 'advisory' and l.classid = 7461 and l.objid = 1;` (the old key shows as `l.classid = 0 and l.objid = 7461`; a leftover there blocks nothing any more, and `select pg_terminate_backend(<pid>)` clears it).

**Healthchecks.** A new deployment receives traffic only once Railway's healthcheck gets a 2xx from it; without a healthcheck Railway switches traffic as soon as the container starts, before the api has migrated and listens (about 9 s, and up to `MIGRATION_LOCK_TIMEOUT_MS` more), and a deployment that crash-loops replaces a healthy one. Until 2026-10-12 no service had one. Every service with an HTTP server now has its own config file, `railway/<service>.toml`: the shared build and teardown of `railway.toml` plus `healthcheckPath = "/health"` (`healthcheckTimeout` 180 s for the api, which migrates before it listens, 120 s for the others; `scripts/railway-config.test.mjs` in CI keeps the copies equal). `/health` answers 503 until the service is ready: api, gateway, composer and ingest without their database, stream without Redis or while shutting down. The orchestrator serves no HTTP and keeps `railway.toml`, with no healthcheck. To turn it on:
1. api, gateway, composer, stream and ingest: Railway → the service → Settings → Config-as-code → **Railway config file** = `/railway/api.toml` (`/railway/gateway.toml`, `/railway/composer.toml`, `/railway/stream.toml`, `/railway/ingest.toml`). The orchestrator stays on `/railway.toml`.
2. Because Railway stops reading config-as-code on 2026-12-01, also set the same values as each of those five services' own settings: Settings → Deploy → **Healthcheck Path** `/health`, **Healthcheck Timeout** 180 (api) or 120 (the others). Leave both empty on the orchestrator.
3. Check on the next deploy: the deployment shows "Healthcheck succeeded" before it becomes active, and the previous deployment keeps answering until then.

**Database round trips.** The services run in Railway's EU West region (Amsterdam), the nearest Railway region to the database, and reach Supabase's transaction pooler in eu-north-1 (Stockholm) at about 28 ms per round trip (from the api's own request logs, 2026-10-11). A procedure's latency is therefore mostly its number of round trips, and until 2026-10-12 business.get made about 20 (≈ 560 ms; Home's first batch 1.7-3 s). Three code changes cut every business procedure to about 4 (docs/DECISIONS.md "Round trips per procedure"; counted per procedure by `apps/api/src/__tests__/round-trips.test.ts`): postgres.js no longer asks the server for parameter types before sending values (`patches/postgres@3.4.9.patch`, applied by pnpm), so a statement costs one round trip and the statements of a transaction go together; `withRls` sends its role and claims with the transaction's first statement; and membership and business are looked up in one statement. Keep `DATABASE_URL` on the transaction pooler (port 6543): `createDb` turns prepared statements off for it, which the patch relies on. If latency still matters after that, the remaining lever is distance: a Supabase project in eu-central-1 (Frankfurt) would sit about 8 ms from Amsterdam, at the cost of moving the database.

**Redeploys and shutdown.** On a redeploy Railway keeps the previous deployment running for `overlapSeconds` (15) after the new one is active (with a healthcheck: once it answers `/health`), then sends it SIGTERM and, `drainingSeconds` (60) later, SIGKILL (both in railway.toml, which overrides the dashboard). In the image tini is PID 1 and the service's node process its direct child (`ENTRYPOINT ["/usr/bin/tini", "--"]`, `CMD ["sh", "-c", "cd apps/${APP} && exec node --import tsx src/index.ts"]`). Until 2026-10-11 the command was `sh -c "pnpm --filter … start"`: sh was PID 1 and ignored SIGTERM, and corepack's pnpm shim does not pass it on, so every service ran on until SIGKILL and was cut off mid-request (verified locally in a PID namespace: no "shutting down" line, killed 10 s later). Each service now handles SIGTERM itself (`@foundmill/shared/shutdown`) within `SHUTDOWN_TIMEOUT_MS` (default 45 s) and exits 0, logging "<service> shutting down", one line per step and "<service> shutdown complete":
- api, gateway, composer, ingest: stop accepting connections, let in-flight requests finish (streamed tRPC answers included; idle keep-alive connections are closed at once), then stop the outbox relay (api), close Temporal, Redis and the database pool. Connections still open 5 s before the budget ends are cut (logged with a count).
- stream: refuse new upgrades and close every WebSocket with 1001 "going away"; the browser client reconnects with backoff, to the new deployment. Then stop the Redis readers and close Redis and the pool.
- orchestrator: stop polling; running activities get 30 s (`SHUTDOWN_TIMEOUT_MS` − 15 s) to finish, are then canceled, and an activity that stops is reported failed so Temporal retries it on the new worker at once (verified with a local Temporal: a 6 s activity finished during the drain; with a 2 s grace it was handed back as attempt 2). Then the Temporal connection, Redis and the pool close.
A custom Start Command in a service's Railway settings replaces the image's ENTRYPOINT (tini) and must stay empty. Railway reads railway.toml only until 2026-12-01 (config-as-code is deprecated in favor of `.railway/railway.ts`, which does not document the draining keys yet); the same values are therefore also set as each service's own settings (Settings → Deploy → Teardown: draining 60 s, overlap 15 s), done through Railway's API on 2026-10-11 for api, gateway, composer, stream, ingest and orchestrator and checked afterwards (no redeploy was triggered; every Start Command confirmed empty). Nothing more is needed when railway.toml stops being read.

Without Temporal the api still answers every procedure (Continue runs one in-process cycle step and says so); without Redis the stream has no fan-out and the api logs one line and keeps serving.

GitHub sends you back to the callback URL, and "Connect installation" finishes it; only the founder who started it can finish it, within 15 minutes. Then, on Development › Code ("Set up GitHub"), choose the repository and tick "Push agents' saved code to this repository". A push can start that repository's CI and preview deploys on code an agent wrote, so turn it on only for a repository whose CI secrets you are content to expose to agent code. `[skip ci]` skips GitHub Actions push and pull-request runs only: workflows on other events (`on: create`), scripts they run from anywhere in the repository, and services that ignore it (Vercel) still build. The gateway enforces the choice: `commit_files` writes only to the chosen repository while pushing is on.

5. **Paying for credits, and spend ceilings.** Credits are US dollars and pay for model calls on the platform key. Settings › Billing › Top up opens a checkout and grants nothing by itself:
   - **Real payments** (gateway `INTEGRATIONS_MODE=live`, or `LIVE_CONNECTORS=stripe` with every other connector still mock): the api asks the gateway for a Stripe Checkout session on the platform account (`STRIPE_SECRET_KEY`, gateway only) and sends the founder to Stripe's page; Stripe sends them back to Settings › Billing, which waits for the payment. Credits are granted only by the platform webhook: in the Stripe dashboard (Developers → Webhooks → Add endpoint) add `https://ingest.foundmill.com/billing/stripe` with the events `checkout.session.completed`, `checkout.session.async_payment_succeeded` and `checkout.session.expired`, and put its signing secret in `STRIPE_BILLING_WEBHOOK_SECRET` on ingest. Without that secret ingest refuses every billing delivery (503), so nothing can be granted by a forged request. Use a test-mode key and endpoint on staging. Each paid session is granted once (`billing_checkouts`, migration 0033) and audited as `billing.credits_purchased`.
   - **Mock payments** (Stripe not live): the checkout is simulated on the Billing tab ("Complete mock payment", labeled, no money moves). They are refused while `MODEL_MODE=live` outside development and test, because free credits would pay for real model calls; with live models and no Stripe the Billing tab says top-ups are not available and points to Settings › Keys.
   - **Paid tiers** (Pro, Scale) cannot be chosen while their prices are "to be announced" (development and test excepted); moving to Free is always allowed.
   - **Ceilings.** Every model-backed procedure (Ideation, Compare, Ask, logos, conversations, Inbox Refresh, plan previews, task planning, the recommenders, foundations retries, training, Continue) and registry lookups and checkouts have per-person and per-business allowances; a refusal answers "<what> limit reached. Try again in N minutes." The windows live in the api's Redis (`REDIS_URL`) so every replica counts against the same ones; when Redis does not answer they fall back to memory for 30 s (logged), so the limits still hold per replica. As a backstop, set a monthly spend limit on the Anthropic account behind `ANTHROPIC_API_KEY` (console.anthropic.com → Settings → Limits) and on the E2B team behind `E2B_API_KEY` (e2b.dev dashboard → Billing → usage limit).

## 7. Local stack without Postgres or Redis

```
pnpm install
SEED_TARGET=pglite pnpm db:seed                       # writes ./.pglite/dev and prints the DATABASE_URL to reuse
DATABASE_URL=pglite:./.pglite/dev APP_ENV=development DEV_AUTH_USER_ID=<printed owner id> pnpm --filter @foundmill/api dev
NEXT_PUBLIC_APP_ENV=development pnpm --filter @foundmill/web dev
```

PGlite allows one process per data directory, so only the api opens `./.pglite/dev`; the web talks to the api. The exact e2e stack is in `apps/web/e2e/README.md`.
