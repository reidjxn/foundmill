# DEPLOY.md — staging on Vercel + Railway + Supabase

What has to be configured outside the repository before foundmill.com runs the real app. Deployment is push-driven (docs/DECISIONS.md "Cloud-first build and deploy"): Vercel builds `apps/web` from `main`; every backend service builds from the root `Dockerfile` with the `APP` variable and runs its package's entry (`node --import tsx src/index.ts` in `apps/<app>`, what `pnpm --filter @foundmill/<app> start` runs) under tini (§3 "Redeploys and shutdown"). Nothing here contains a secret value; the values live in the Vercel and Railway dashboards.

## 1. Merge to `main`

Vercel's production branch is `main`. The cloud build lands on `main-emurwq`; merge it through a pull request (CI runs on every pull request) once its checks are green: `pnpm typecheck && pnpm lint && pnpm test`, the Next build and the Playwright suites. Every commit must be authored as `Reid Jackson <40631036+reidjxn@users.noreply.github.com>` or Vercel blocks the deployment (DECISIONS.md "Commit identity").

**Only a green commit deploys.** Until 2026-10-12 nothing enforced the line above: Railway and Vercel deployed every push to `main` while CI ran, and the pushes of 7e5760c, c9dd4bb and 76a112c all shipped with CI red (the unit job and the Playwright job). Three settings close that, all outside the repository:

1. **Railway "Wait for CI", on each of the six app services** (api, gateway, composer, stream, ingest, orchestrator). Railway → project `founder-manager` → the service → Settings → Source → turn on **Wait for CI** (the toggle sits under the connected branch, and appears once the repository has GitHub Actions workflows). With it on, a push to `main` shows as "Waiting for CI" and deploys only after every GitHub Actions run on that commit has passed; if one fails, the deployment is skipped and the running one stays. Through Railway's API it is the service's deployment trigger: `deploymentTriggerUpdate(id: <trigger id>, input: { checkSuites: true })` (read the trigger id with `deploymentTriggers(serviceId, environmentId)`; on 2026-10-11 all six read `checkSuites: false`). Check afterwards: the next push shows "Waiting for CI" on each service.
2. **Branch protection on `main`** (GitHub → reidjxn/foundmill → Settings → Branches → Add rule for `main`): require a pull request, and require the status checks "Typecheck, lint, unit tests", "Playwright (web screens + golden path)", "Banned terms, vocabulary and US English", "Storybook build" and "Docker image (build and boot)" to pass before merging. A red commit then never reaches `main`, which also gates Vercel: Vercel has no wait-for-CI switch for Git deployments, so its production deploy is only as safe as the branch. GitHub offers protection rules on a private repository only on a paid plan (Pro or Team); without one, nothing refuses a push to `main`, so merge only through a pull request whose checks are green, and Railway's "Wait for CI" (1) still keeps a red commit off the backend.
3. **Optional on Vercel**: where the project's plan offers Deployment Checks (Project → Settings → Deployment Checks), add the GitHub checks above, so a production deployment is promoted to foundmill.com only once they pass. Not verified from here; branch protection (2) is what the web relies on.

Record a check as green in docs/PROGRESS.md only from the CI run of that commit (`gh run list --branch main`), never from a local run.

**One address for sign-in.** foundmill.com is the canonical origin. The app answers every request for www.foundmill.com with a 308 to the same path and query on https://foundmill.com (`redirects()` in `apps/web/next.config.ts`, host-matched, applied before the proxy, so www never sets a cookie). Supabase's PKCE flow keeps the code verifier in a cookie on the host that asked for the magic link, and the api's CORS list is built from `APP_URL`, so sign-in only works when asking for the link, opening it and using the app all happen on one host. The login form therefore always sets the magic link's `emailRedirectTo` to `NEXT_PUBLIC_APP_URL` or, when that is unset, `https://foundmill.com/auth/callback` (development and test without `NEXT_PUBLIC_APP_URL` keep the page's own origin), and `/auth/callback` turns a code it cannot exchange into a notice on `/login` ("Link opened on a different address", "Link expired") above a form that sends a new link (`apps/web/lib/auth/sign-in-errors.ts`). The api also allows the www twin of `APP_URL` (`https://www.foundmill.com`) as a safety net for a page still open on www. Never set the opposite redirect (apex → www) in Vercel: the two would loop. Optionally also set www.foundmill.com to "Redirect to foundmill.com" (308) under Vercel → Project → Settings → Domains; the edge then answers before the app and the result is the same.

**Migrations at boot.** The api applies pending migrations before it listens; no manual `pnpm db:migrate` is needed. The whole run is one transaction that first takes `pg_advisory_xact_lock(7461, 1)` (packages/db `migrator.ts`), so on Supabase's transaction pooler (port 6543) every statement of the run, the lock included, stays on one server connection, and the lock ends with the transaction: on commit, on rollback, and when the process dies (Postgres 14+ notices a dead client within a second even mid-statement). Until 2026-10-11 the api took a session-level `pg_advisory_lock(7461)` and released it with a separate statement; through the pooler the two could land on different server connections, so the lock stayed held by a pooled connection and the next boot waited forever before "api listening". Waiting is bounded: `MIGRATION_LOCK_TIMEOUT_MS` (api, optional, default `60000`) caps the wait for the lock and for any table lock a migration needs; past it the api logs "migration lock not granted within 60 s; exiting with code 1", with the sessions holding the lock (pid, application, start time, query), and exits 1, so Railway restarts it (`restartPolicyType = "ON_FAILURE"`, 10 retries: the setting in force on every service, and since 2026-10-12 the value in the railway files too) instead of the deploy hanging. A migration that Postgres aborts to break a deadlock (the previous deployment keeps serving during a redeploy) is treated the same way: "migration aborted by a deadlock with another connection; exiting with code 1", and the restarted boot applies it. Nothing is applied by a run that gives up; a migration that fails rolls back the whole run and the api serves on the old schema (/health still reports the database). Only the api migrates Postgres: composer, gateway, stream, ingest and orchestrator log "database ready" after a read-only probe of the bookkeeping table (they migrate only a PGlite directory they own). `pnpm db:migrate` takes the same lock, so it waits for a booting api and vice versa. To see who holds the lock, in the Supabase SQL editor: `select l.pid, a.application_name, a.state, a.backend_start, a.query from pg_locks l join pg_stat_activity a using (pid) where l.locktype = 'advisory' and l.classid = 7461 and l.objid = 1;` (the old key shows as `l.classid = 0 and l.objid = 7461`; a leftover there blocks nothing any more, and `select pg_terminate_backend(<pid>)` clears it).

**Healthchecks.** A new deployment receives traffic only once Railway's healthcheck gets a 2xx from it; without a healthcheck Railway switches traffic as soon as the container starts, before the api has migrated and listens (about 9 s, and up to `MIGRATION_LOCK_TIMEOUT_MS` more), and a deployment that crash-loops replaces a healthy one. Until 2026-10-12 no service had one. Every service now has its own config file, `railway/<service>.toml`: the shared build and teardown of `railway.toml` plus `healthcheckPath = "/health"` (the orchestrator: `"/ready"`) and the service's watch patterns (below) (`healthcheckTimeout` 180 s for the api, which migrates before it listens, and for the orchestrator, which bundles its workflows and connects to Temporal first; 120 s for the others; `scripts/railway-config.test.mjs` in CI keeps the copies equal). `/health` answers 503 until the service is ready: api, gateway, composer and ingest without their database, stream without Redis or while shutting down. The orchestrator's `/ready` answers 503 until both its workers run (Temporal reachable) and while its database or a worker is down; its `/health` also answers 503 whenever a task queue's oldest waiting activity has waited past its limit (5 minutes on `foundmill`, 15 on `foundmill-sessions`), for an uptime monitor (Railway checks only at deploy time, and a new deployment that comes to clear a wedged queue must not be held back by that queue's age, hence `/ready` for the deploy). Both bodies say why, with each worker's free slots and each queue's backlog. To turn it on:
1. Each of the six: Railway → the service → Settings → Config-as-code → **Railway config file** = `/railway/<service>.toml` (`/railway/api.toml`, `/railway/gateway.toml`, `/railway/orchestrator.toml`, `/railway/composer.toml`, `/railway/stream.toml`, `/railway/ingest.toml`). `/railway.toml` stays as the shared base for a service without a file of its own.
2. Because Railway stops reading config-as-code on 2026-12-01, also set the same values as each service's own settings: Settings → Deploy → **Healthcheck Path** `/health` (orchestrator: `/ready`), **Healthcheck Timeout** 180 (api, orchestrator) or 120 (the others); Settings → Build → **Watch Paths** as listed in its file.
3. Check on the next deploy: the deployment shows "Healthcheck succeeded" before it becomes active, and the previous deployment keeps answering until then.

**Watch patterns.** Until 2026-10-12 every push to `main` redeployed all six services, so a docs-only commit restarted the orchestrator and, with it, every agent session in flight. Each service's file now lists what its image is built from: `/apps/<service>/**`, `/packages/**`, `/patches/**`, `/Dockerfile`, its own railway file, `/package.json`, `/pnpm-lock.yaml`, `/pnpm-workspace.yaml` and `/.npmrc`. A push that touches only docs, `apps/web` or another service leaves it running (Railway shows the deployment as skipped: no changes to watched files). A change to any shared package still redeploys all six.

**Database round trips.** The services run in Railway's EU West region (Amsterdam), the nearest Railway region to the database, and reach Supabase's transaction pooler in eu-north-1 (Stockholm) at about 28 ms per round trip (from the api's own request logs, 2026-10-11). A procedure's latency is therefore mostly its number of round trips, and until 2026-10-12 business.get made about 20 (≈ 560 ms; Home's first batch 1.7-3 s). Three code changes cut every business procedure to about 4 (docs/DECISIONS.md "Round trips per procedure"; counted per procedure by `apps/api/src/__tests__/round-trips.test.ts`): postgres.js no longer asks the server for parameter types before sending values (`patches/postgres@3.4.9.patch`, applied by pnpm), so a statement costs one round trip and the statements of a transaction go together; `withRls` sends its role and claims with the transaction's first statement; and membership and business are looked up in one statement. Keep `DATABASE_URL` on the transaction pooler (port 6543): `createDb` turns prepared statements off for it, which the patch relies on. If latency still matters after that, the remaining lever is distance: a Supabase project in eu-central-1 (Frankfurt) would sit about 8 ms from Amsterdam, at the cost of moving the database.

**The platform's Anthropic account out of credit (2026-10-12).** When Anthropic refuses to bill a call on the platform key (400 "Your credit balance is too low", 400 "You have reached your specified API usage limits", or 429 with `error_code: "enforced_spend_limit_reached"`, which has no retry-after), the models client throws a `ModelBillingError` at once: nothing retries it, because it lasts until someone pays or the month ends. Founders read a plain sentence (the model account is out of credit, the team has been alerted, nothing was charged to their credits; a business on its own key is told to add credit in its Anthropic Console) instead of "Something went wrong on our side"; a cycle that cannot be planned ends `failed` with a warning from the Chief of Staff in the Inbox. For you: every refused call logs one error line with `alert: "model_billing"`, `reason` (`credit_balance` or `spend_limit`), `route` and `requestId` (match it in Railway's log search or a log drain), and `/health` on the api and the composer carries `modelBilling: { ok: false, reason, since, lastAt, route, count }` until the next platform-key call is billed (the services stay up, so it does not fail the healthcheck). The fix is in the Anthropic Console: add credit or raise the spend limit. A business's own key that cannot pay is the founder's to fund: it logs a warning and never alerts.

**Redeploys and shutdown.** On a redeploy Railway keeps the previous deployment running for `overlapSeconds` (15) after the new one is active (with a healthcheck: once it answers `/health`), then sends it SIGTERM and, `drainingSeconds` (60) later, SIGKILL (both in railway.toml, which overrides the dashboard). In the image tini is PID 1 and the service's node process its direct child (`ENTRYPOINT ["/usr/bin/tini", "--"]`, `CMD ["sh", "-c", "cd apps/${APP} && exec node --import tsx src/index.ts"]`). Until 2026-10-11 the command was `sh -c "pnpm --filter … start"`: sh was PID 1 and ignored SIGTERM, and corepack's pnpm shim does not pass it on, so every service ran on until SIGKILL and was cut off mid-request (verified locally in a PID namespace: no "shutting down" line, killed 10 s later). Each service now handles SIGTERM itself (`@foundmill/shared/shutdown`) within `SHUTDOWN_TIMEOUT_MS` (default 45 s) and exits 0, logging "<service> shutting down", one line per step and "<service> shutdown complete":
- api, gateway, composer, ingest: stop accepting connections, let in-flight requests finish (streamed tRPC answers included; idle keep-alive connections are closed at once), then stop the outbox relay (api), close Temporal, Redis and the database pool. Connections still open 5 s before the budget ends are cut (logged with a count).
- stream: refuse new upgrades and close every WebSocket with 1001 "going away"; the browser client reconnects with backoff, to the new deployment. Then stop the Redis readers and close Redis and the pool.
- orchestrator: stop polling, then hand the agent sessions off. Each running session saves its place (the recording position, its progress, nudges not yet delivered, and for a live session its workspace) and returns a hand-off within seconds; its workflow starts the next run at once, which the new deployment's worker picks up and continues from that place, with a "Session continued on a new worker" note on the session. A sandbox running acceptance tests is stopped first. A session cut by the worker's cancellation is handed off the same way instead of ending `stopped` or `failed`, so its agent is not marked failing. Other activities get 30 s (`SHUTDOWN_TIMEOUT_MS` − 15 s) to finish and are then canceled; their retry policies run them again on the new worker. A session whose worker died outright (SIGKILL, a crash) times out on its heartbeat and is tried again, up to three attempts, from its last heartbeat (`session-runner-retry`). Until 2026-10-12 this bullet said every stopped activity was retried on the new worker: it was not true of agent sessions, which ended at the deploy. Then the Temporal connection, Redis and the pool close.
A custom Start Command in a service's Railway settings replaces the image's ENTRYPOINT (tini) and must stay empty. Railway reads railway.toml only until 2026-12-01 (config-as-code is deprecated in favor of `.railway/railway.ts`, which does not document the draining keys yet); the same values are therefore also set as each service's own settings (Settings → Deploy → Teardown: draining 60 s, overlap 15 s), done through Railway's API on 2026-10-11 for api, gateway, composer, stream, ingest and orchestrator and checked afterwards (no redeploy was triggered; every Start Command confirmed empty). Nothing more is needed when railway.toml stops being read.

**Observability.** Nothing is sent anywhere until these are set; each is optional and read by every Node service (packages/shared `telemetry.ts`, no vendor SDK):
- **Logs.** JSON lines on stdout with the level as a word, so Railway's severity filter works (until 2026-10-12 every app warning and error showed as info, and the Temporal SDK's info lines as errors: they now go through the same logger). Useful searches: `"level":"error"`, `orchestrator is not working through its task queues`, `outbox relay`.
- **Errors.** `SENTRY_DSN` (Sentry → project → Settings → Client Keys): every error-level log line and uncaught exception becomes an event, with only the ids and codes in the log line (never payloads or arguments), deduplicated and rate-limited per process.
- **Traces.** `OTEL_EXPORTER_OTLP_ENDPOINT` and `OTEL_EXPORTER_OTLP_HEADERS` (OTLP over HTTP/JSON). For Grafana Cloud: Home → Connections → OpenTelemetry (OTLP) gives the endpoint (`https://otlp-gateway-<zone>.grafana.net/otlp`) and an access token with `traces:write` and `metrics:write`; the header is `Authorization=Basic%20<base64 of instanceId:token>`. Spans: every api request (incoming `traceparent` honored), every orchestrator activity, every gateway tool call (an agent session's run is the parent of its model calls and its tool calls), and every model call with its tokens and cost (an Estimate). The orchestrator also exports the Temporal SDK's metrics (task-queue poll latency, slots used) to the same endpoint.
- **Alerts.** The api checks the orchestrator's task queues every minute and logs an error, "orchestrator is not working through its task queues", when the oldest waiting activity has waited more than 5 minutes (15 on the sessions queue), again every 15 minutes while it lasts, and an info line, "orchestrator task queues are served again", when work moves again; with `SENTRY_DSN` set each becomes a Sentry issue. The api's `/health` carries the same `worker` verdict, and the outbox relay's state (`relay.state`: `running`, or `waiting_for_redis` with its attempt count while Redis is away); the orchestrator's own `/health` answers 503 meanwhile.

**Temporal and its database.** Temporal runs from Docker Hub images on Railway (`temporal`: `temporalio/auto-setup`, `temporal-ui`: `temporalio/ui`) with its state in the Railway Postgres service (about 1.2 GB on 2026-10-11). Both images were `:latest` until 2026-10-15 (now pinned, see the §6 checklist): a restart, or any variable change, pulls whatever is newest, and auto-setup then runs schema updates against the live database. In Railway → `temporal` → Settings → Source, set the image to an explicit tag: the version the running deployment reports (`temporal operator cluster system`, or the version in the Temporal UI's footer; the running digest was `sha256:9be7b8d98f60…` on 2026-10-08), for example `temporalio/auto-setup:<that version>`; do the same for `temporal-ui`. Upgrade later on purpose, one minor version at a time, after a backup. Railway → Postgres → the volume → Backups: add a daily schedule (keep at least 7). Losing that volume loses every workflow in flight (sessions, vacations, cycles).

**Redis memory.** Redis runs `noeviction`, so a full Redis refuses writes (the outbox relay, live tiles and the control bus stop) instead of losing streams. Since 2026-10-12 nothing in it grows without bound: an agent session's stream (`as:<session id>`) is saved to Postgres when the session finishes (`session_recordings`, where replays read it) and expires an hour later, with a 14-day expiry on every publish as a backstop; a business's stream (`ev:<business id>`) keeps 30 days (every event is also in Postgres) and expires 30 days after its last event, and is deleted when the business is archived. Set `maxmemory` on the Redis service (Railway → Redis → Variables or its config, for example 75% of the plan's memory) and keep `maxmemory-policy noeviction`; alert when `used_memory` passes 80% of it (Railway's metrics, or Grafana with the Redis integration).

Without Temporal the api still answers every procedure (Continue runs one in-process cycle step and says so); without Redis the stream has no fan-out and the api logs one line and keeps serving; the api's outbox relay retries Redis with a backoff (1 s doubling to 30 s) until it answers, so live updates resume by themselves.

## 4. Supabase

- Auth → URL configuration: site URL `https://foundmill.com`, redirect URLs `https://foundmill.com/auth/callback` and `https://www.foundmill.com/auth/callback`. Since 2026-10-10 every new magic link points at `https://foundmill.com/auth/callback`; keep the www entry anyway, because a link emailed earlier from www carries the www address and Supabase checks it when the link is opened (the app then redirects it to the apex, where it shows "Link opened on a different address" and offers a new link).
- Auth → Providers: Email with magic links enabled. Sign-in is magic link only.
- **Who can sign in.** Supabase creates an account for any address that asks for a magic link ("Allow new users to sign up" is on by default), and every signed-in account can drive model calls on the platform's Anthropic key. While staging runs `MODEL_MODE=live`, set `SIGNUP_ALLOWLIST` on the api to the people who may use it: exact addresses and whole domains, comma-separated (`you@example.com, @example.org`; case does not matter; `@example.org` does not admit `sub.example.org`). Every signed-in request from any other account is refused before it does anything (FORBIDDEN, `not_invited`), and the web shows an "Invite only for now" page with a Sign out button. Set the same value on stream and collab: they refuse that account's sockets too (a person taken off the list keeps no live channel or spec editor once the services restart with the new list). Invited staff need their address (or domain) on the list too. Unset or empty admits everyone. As a second lock, turn off Auth → Providers → Email → "Allow new users to sign up" and add people under Auth → Users → Invite; the allow-list still applies to them.
- **Confirm email stays on (required with `SIGNUP_ALLOWLIST`).** Auth → Providers → Email → "Confirm email" must be enabled, and "Allow anonymous sign-ins" (Auth → Settings) must stay off. The allow-list trusts an address only when the token shows it was confirmed: the session came from a magic link, an email code, the sign-up confirmation, an invite, a recovery or an email change (the token's `amr`, which only Supabase Auth writes; `user_metadata.email_verified` is not trusted because users can edit their own metadata). Keep the Phone provider off, since an SMS code also reads as `otp`. An anonymous sign-in, or a password sign-in to an address nobody confirmed, is refused with "This address is not confirmed yet" on the invite-only page, so nobody can claim a listed address they cannot read. With Confirm email off anyone could sign up with a password for an address they cannot read; the allow-list still refuses such a session, but keep it on so those accounts are never created.
- **Auth → Emails → SMTP Settings: a custom SMTP sender. Required before anyone but the founder can sign in.** Supabase's built-in sender only mails addresses that belong to the Supabase organization's own team, and at most 2 emails an hour; every other founder asking for a link gets "Email address not authorized" (the login form shows "We can't send sign-in emails to this address right now. Please contact support.") and, past the hourly cap, "Too many sign-in links were requested". The repository records no custom SMTP as of 2026-10-12, and the only proven sign-in is the owner's own address, so check this first.
  1. Pick a transactional email provider (Resend, Postmark, Amazon SES or SendGrid) and verify the sending domain `foundmill.com` there: add the SPF, DKIM and return-path records it gives you at Spaceship (DNS for foundmill.com is hosted there, §2).
  2. Supabase → project → Authentication → Emails → SMTP Settings → **Enable custom SMTP**: host, port (465 or 587), username and password (the provider's SMTP credentials; only the founder enters them), sender email `no-reply@foundmill.com`, sender name "Foundmill".
  3. Authentication → Rate Limits: raise **Rate limit for sending emails** (30 an hour once custom SMTP is on) to what launch needs, for example 200 an hour. The per-address resend window (one link a minute) stays.
  4. Authentication → Emails → Templates → Magic Link: keep `{{ .ConfirmationURL }}` as the link (it carries `emailRedirectTo`, §2); write the copy in US English.
  5. Check: from an address outside the Supabase organization, request a link on foundmill.com/login; it arrives within a minute and signs in. Supabase → Logs → Auth shows the send.

## 5. First sign-in and live agents

1. Open foundmill.com and sign in with a magic link. A new founder lands on the onboarding profile, then `/new` (Ideation Studio or Import), then Commit, which creates the business, its departments and its agent team. The exception is an address in the api's `SEED_OWNER_EMAILS` while `SEED_ON_BOOT=1`: the first boot on an empty database builds the demo businesses (Northwind Skincare, Ledgerly) with that address as owner, so signing in with it lands on Northwind's Home, and the founder can still start their own business from `/new`.
2. **Live models.** api, composer and orchestrator call Anthropic with the platform key `ANTHROPIC_API_KEY` from their Railway variables when `MODEL_MODE=live` (set on all three since 2026-10-08). Add the key as a project shared variable and reference it from those three services (`ANTHROPIC_API_KEY=${{shared.ANTHROPIC_API_KEY}}`); until it is there they run on the mock client and log one error at boot. Settings → Keys (`/b/<business id>/settings/keys`) stores a per-business key, which the orchestrator uses only when the business's model billing is `byok`; the api and composer always use the platform key, and charge those calls to the business's credits (item 5). Model ids live in `packages/models/src/routing.ts` (Opus 5.5, Sonnet 5.5, Haiku 4.5; re-verified 2026-10-08).
3. **Real agent sessions.** With `INTEGRATIONS_MODE=mock` the orchestrator replays recorded sessions. Set `SANDBOX_MODE=e2b` and `E2B_API_KEY` on the orchestrator for real sandboxes while connectors stay in mock; `INTEGRATIONS_MODE=live` switches every connector to its vendor API and needs each vendor's variables (item 6 lists them, and where each goes). The E2B Hobby plan is enough: the agent itself runs next to the orchestrator, and a session creates a sandbox only for a code task's acceptance run (copy the workspace, install, run the tests), asking for 30 minutes, inside Hobby's one-hour cap (Pro allows 24 hours). Research, writing and other tasks never create one. Hobby allows 20 sandboxes at once, more than the acceptance runs one replica can have running with the default `ORCHESTRATOR_MAX_SESSIONS=16`; with more than one orchestrator replica, lower `ORCHESTRATOR_MAX_SESSIONS` or move to Pro (100 at once).

4. **Agents' code on GitHub.** After a session on a code task finishes, the orchestrator pushes the saved code to the task's own branch (`agent/<task id>`) of the private repository chosen on Development › Code, once the founder has turned pushing on there. It goes through the gateway's GitHub connector (`commit_files`): one commit per session, only what changed, at most 300 files and 10 MB, marked `[skip ci]`, nothing under `.git` or `.github`, never the default branch, never a force-push. A session that was stopped, looped or failed is saved but not pushed. In mock mode the pushes land in the simulated GitHub and the Code tab says so. To push to real GitHub while every other connector stays mock:
   1. Create a GitHub App (github.com → Settings → Developer settings → GitHub Apps → New).
      - Repository permissions: **Contents: Read and write**, **Pull requests: Read and write**, **Metadata: Read**. Organization permission: **Members: Read** (connecting checks the installer is an owner of the organisation).
      - Callback URL: `https://foundmill.com/integrations/github/callback`, and tick **Request user authorization (OAuth) during installation**. Connecting checks with GitHub that the person connecting owns the installation's account (a personal installation) or is an active owner of its organisation. Only then does the gateway record the installation (`app_installations`, which no app role can write) and mint tokens for it.
      - "Any account" lets founders install it on their own accounts and organisations.
      - Pre-filled registration link (personal account): `https://github.com/settings/apps/new?name=Foundmill&url=https%3A%2F%2Ffoundmill.com&callback_urls[]=https%3A%2F%2Ffoundmill.com%2Fintegrations%2Fgithub%2Fcallback&request_oauth_on_install=true&public=true&webhook_active=false&contents=write&pull_requests=write&metadata=read&members=read`.
      - Leave the Setup URL empty: with OAuth during installation, GitHub uses the callback URL.
      - Leave webhooks inactive. A GitHub App has one webhook URL for every installation, and ingest routes GitHub deliveries by the business id in the URL, so the App's webhook needs routing by installation (`app_installations`) before it is turned on.
      - Generate a private key and a client secret.
   2. Install the App on the account that owns the repository (all repositories, or only the ones agents may write to). Agents push only to private repositories.
   3. On the **gateway** only: `GITHUB_APP_ID`, `GITHUB_APP_PRIVATE_KEY` (the PEM; `\n` escapes are accepted), `GITHUB_APP_SLUG` (the App's URL name), `GITHUB_APP_CLIENT_ID`, `GITHUB_APP_CLIENT_SECRET`, `LIVE_CONNECTORS=github`. The api needs only `LIVE_CONNECTORS=github` (with `GATEWAY_URL` and `SESSION_TOKEN_SECRET`, already set): it asks the gateway to connect the installation and never holds the App's keys.
   4. In the app: Settings › Integrations › GitHub › Connect opens the App's installation page. GitHub sends you back to the callback URL, and "Connect installation" finishes it; only the founder who started it can finish it, within 15 minutes. Then, on Development › Code ("Set up GitHub"), choose the repository and tick "Push agents' saved code to this repository". A push can start that repository's CI and preview deploys on code an agent wrote, so turn it on only for a repository whose CI secrets you are content to expose to agent code. `[skip ci]` skips GitHub Actions push and pull-request runs only: workflows on other events (`on: create`), scripts they run from anywhere in the repository, and services that ignore it (Vercel) still build. The gateway enforces the choice: `commit_files` writes only to the chosen repository while pushing is on.

5. **Paying for credits, and spend ceilings.** Credits are US dollars and pay for model calls on the platform key. Settings › Billing › Top up opens a checkout and grants nothing by itself:
   - **Real payments**: set `LIVE_CONNECTORS=stripe_billing` on both the **api** and the **gateway** (or run them with `INTEGRATIONS_MODE=live`), and `STRIPE_SECRET_KEY` on the gateway only. `stripe_billing` is the platform's own billing switch: the businesses' own Stripe connector (`stripe`) stays mock, and turning it live never takes payments. The api asks the gateway for a Stripe Checkout session on the platform account and sends the founder to Stripe's page; Stripe sends them back to Settings › Billing, which waits for the payment. Credits are granted only by the platform webhook: in the Stripe dashboard (Developers → Webhooks → Add endpoint) add `https://ingest.foundmill.com/billing/stripe` with the events `checkout.session.completed`, `checkout.session.async_payment_succeeded`, `checkout.session.async_payment_failed` and `checkout.session.expired`, and put its signing secret in `STRIPE_BILLING_WEBHOOK_SECRET` on ingest. Without that secret ingest refuses every billing delivery (503), so nothing can be granted by a forged request. Use a test-mode key and endpoint on staging. Each paid session is granted once (`billing_checkouts`, migration 0033) and audited as `billing.credits_purchased`.
   - **Mock payments** (the platform's billing not live): the api simulates the checkout itself, without the gateway, on the Billing tab ("Complete mock payment", labeled, no money moves). They exist only where `ALLOW_MOCK_PAYMENTS` on the api allows them: unset means on in development and test and off everywhere else, `1`/`true` turns them on (a staging demo), `0`/`false` off. The api's own `MODEL_MODE` is not the test, because the orchestrator runs live sessions on the platform key whenever `SANDBOX_MODE` is `e2b` or `docker`. Wherever they are on, the credits they grant are labeled on the Billing tab and never pay for a live model call: the api, the composer and the orchestrator count only real credits when their calls are live, so a business left with simulated credits only is told "Only simulated credits are left this month". With simulated payments off and no Stripe the Billing tab says top-ups are not available and points to Settings › Keys.
   - **Paid tiers** (Pro, Scale) cannot be chosen while their prices are "to be announced" (development and test excepted); moving to Free is always allowed.
   - **The credits ceiling.** Every model call on the platform key for a business asks first: once the business's credits for the month are used up, the api, the composer and the orchestrator refuse the call before it is made ("This month's credits are used up…", 402), whatever the business's model billing. A business on its own key runs its agents on that key, but conversations, Refresh and planning run on the platform key and use its credits. Included credits are one pool a month per founder: the businesses one person took charge of (archived ones included) share as many included credits as their plan holds businesses, so archiving and starting again never yields a second grant in the same month. A live agent session on the platform key is capped at the credits left when it starts (the Agent SDK's `maxBudgetUsd`), books what it spends every turn and every 15 seconds, and ends `blocked` (reason `budget`) when they run out. Starting a task by hand, and every session the orchestrator opens, counts against the plan's concurrent agents.
   - **Ceilings.** Every model-backed procedure (Ideation, Compare, Ask, logos, conversations, Inbox Refresh, plan previews, task planning, the recommenders, foundations retries, training, Continue, starting a task, Take charge) and registry lookups and checkouts have per-person and per-business allowances; a refusal answers "<what> limit reached. Try again in N minutes." The windows live in the api's Redis (`REDIS_URL`) so every replica counts against the same ones; when Redis does not answer they fall back to memory for 30 s (logged), so the limits still hold per replica. As a backstop, set a monthly spend limit on the Anthropic account behind `ANTHROPIC_API_KEY` (console.anthropic.com → Settings → Limits) and on the E2B team behind `E2B_API_KEY` (e2b.dev dashboard → Billing → usage limit).

## 7. Local stack without Postgres or Redis

```
pnpm install
SEED_TARGET=pglite pnpm db:seed                       # writes ./.pglite/dev and prints the DATABASE_URL to reuse
DATABASE_URL=pglite:./.pglite/dev APP_ENV=development DEV_AUTH_USER_ID=<printed owner id> pnpm --filter @foundmill/api dev
NEXT_PUBLIC_APP_ENV=development pnpm --filter @foundmill/web dev
```

PGlite allows one process per data directory, so only the api opens `./.pglite/dev`; the web talks to the api. The exact e2e stack is in `apps/web/e2e/README.md`.
