# ARCHITECTURE.md — build contracts

How the repo fits together and the contracts each package exposes to the others. `docs/BUILD.md` is the product spec; this file is what you code against. Read `docs/DECISIONS.md` for choices already made and `docs/DESIGN.md` for the look.

## 1. Layout and ownership

```
apps/web           Next.js 16 App Router. Shell + every surface. Talks to apps/api over tRPC and to apps/stream over WebSocket.
apps/api           Hono + tRPC. Auth context (Supabase JWT), membership checks, RLS-scoped queries, audit, events. Starts Temporal workflows.
apps/gateway       The only process that holds vendor secrets. Session tokens, Cedar policy, connectors (real or mock), metering, audit. Also serves MCP endpoints.
apps/orchestrator  Temporal worker: businessCycle, agentSession, approvalWait, channelEngine, trainingRun, holiday, playbook, incorporation, journeyBuild, importBusiness, businessFoundations, schedules.
apps/composer      Inbox Composer + Refresh buffer + Journey commentary + chapter titles. HTTP service called by api and orchestrator.
apps/ingest        Webhook receivers (Stripe, SendGrid, GitHub, Shopify, ...) → verified → normalised platform events via the outbox.
apps/stream        WebSocket fan-out of Redis streams (ev:{businessId}, as:{sessionId}) to browser tabs.
apps/collab        Hocuspocus (Yjs) server for spec blocks.
apps/social        LIVE network, communities, leaderboards (Phase 4; skeleton only now).
packages/config    APP_NAME, feature flags, pricing tiers, limits. No dependencies.
packages/shared    Vocabulary types/enums (src/constants.ts, src/types.ts), errors, Result, money, ids, env parsing; server-only subpaths /logger and /crypto (envelope encryption).
packages/dugout    Design system: tokens.css, fonts.css, dugout.css, every component, Storybook.
packages/db        Drizzle schema, SQL migrations, RLS, repos, seeds, PGlite test harness.
packages/events    Event catalogue (Zod), outbox writer, Redis relay, consumer helpers.
packages/models    Model routing (the only place model ids live), Anthropic client with mock mode, rate-limit buckets, cost metering.
packages/agents    Agent templates, prompt templates (§12), skill definitions, calibration, archetype seeds.
packages/policy    Cedar schema + policies + evaluator wrapper + tests.
packages/connectors Connector contract, registry, one folder per connector with real + mock.
packages/entity-linker Manifest builder, [[ent:id|Name]] parser/validator, Haiku sweep, render helpers.
packages/journey   Attribution, xC model, journey builder, synthetic journey data generator.
packages/widgets   Widget registry (key → component, default size, settings schema, data hook) shared by Home and department screens.
packages/modules   Built-in module screens (product, development, distribution, finance, team, legal) registered by module key + tab slug.
packages/sandbox   Sandbox interface; E2B, local Docker, and mock (replay) runners.
evals/             Golden tasks and rubrics per agent template and skill.
e2e/               Playwright suites.
```

Package names are `@foundmill/<dir>`. Every package exports TypeScript source directly:

```json
"exports": { ".": "./src/index.ts", "./*.css": "./src/*.css", "./*": "./src/*.ts" }
```

So `@foundmill/db/repos` resolves to `packages/db/src/repos.ts` (a file that re-exports `./repos/index`). Subpath modules are files, not directories.

## 2. Vocabulary (`packages/shared/src/types.ts`)

Every enum used by more than one package is defined once here as a `const` tuple with a matching Zod enum and TS type: game modes, business modes, plan tiers, archetypes, module keys, membership roles, inbox item types/states, agent statuses, model keys, channel keys and lines, task kinds/statuses, plan action types, conversion kinds, Customer Update levels (`matchday_level`), entity kinds, skill groups, integration statuses, visibility, event types. Import from `@foundmill/shared`. Do not redeclare these elsewhere. The tuples, their TS types and the plain records built from them (`MODULE_TABS`, `CHANNEL_META`, `ARCHETYPE_LABELS`…) live in `src/constants.ts` without Zod, and browser code imports them from `@foundmill/shared/constants` so a page does not download Zod; the Zod enums stay in `src/types.ts` and the barrel exports both. Server-only code is not in the barrel: the pino logger is `@foundmill/shared/logger` and envelope encryption (libsodium, AWS KMS) is `@foundmill/shared/crypto`.

Money is `{ amountMinor: number; currency: string }` (minor units, `bigint` in the DB, `number` in TS; values are below 2^53). Ids are UUID strings. Times are ISO strings on the wire and `Date` in TS.

## 3. Modes and environment

- `APP_ENV`: `development | test | staging | production`.
- `INTEGRATIONS_MODE`: `mock | live`. The connector registry returns `connector.mock` in mock mode. Default mock.
- `MODEL_MODE`: `mock | live`. `packages/models` returns recorded/deterministic completions in mock mode. Default mock. Evals always force live.
- Env is parsed once per process with Zod in `packages/shared/src/env.ts` (`loadEnv()`); never read `process.env` directly elsewhere. The web bundle only sees `NEXT_PUBLIC_*`.
- Ports (dev): web 3000, api 4000, gateway 4001, composer 4002, stream 4003, collab 4004, ingest 4005, social 4006. Services read `PORT` first (Railway sets it) and fall back to their named port.

## 4. Database (`packages/db`)

- `createDb(url)` → Drizzle `Db` over postgres.js. `createServiceDb()` reads `DATABASE_URL`.
- `withRls(db, { userId, role?: "authenticated" }, fn)` runs `fn(tx)` inside a transaction after `set local role authenticated` and `set local request.jwt.claims = '{"sub": "<userId>", "role": "authenticated"}'`. `apps/api` uses this for every user-originated query so Postgres RLS enforces tenancy.
- Service code (orchestrator, composer, ingest, gateway) uses the service role **through repositories only**: `repos.<area>.<fn>(db, businessId, ...)` with `businessId` as the required first argument after `db`. The ESLint rule `fm/no-raw-db` forbids `db.select/insert/update/delete/execute` outside `packages/db/src/repos/**`, migrations, seeds, tests and the events outbox.
- Repos live in `packages/db/src/repos/<area>.ts` and are re-exported from `src/repos.ts` as `repos`. Areas mirror BUILD §7.2 groups: `businesses`, `memberships`, `founders`, `ideas`, `product`, `departments`, `screens`, `dashboards`, `agents`, `skills`, `training`, `tasks`, `playbooks`, `holidays`, `inbox`, `plans`, `channels`, `campaigns`, `journeys`, `entities`, `finance`, `capTable`, `usage`, `legal`, `integrations`, `credentials`, `policies`, `approvals`, `audit`, `events`, `social`, `preferences` (account-scoped: the signed-in person's date and time format, §20).
- Audit log: `repos.audit.append(db, businessId, { actorKind, actorId, action, target, details })` computes the hash chain. No update/delete grants.
- Migrations: SQL in `packages/db/migrations/*.sql` + `meta/_journal.json` (drizzle-kit format). `pnpm db:migrate` applies them. Schema in `src/schema/*.ts` mirrors the SQL (the SQL is the source of truth for RLS).
- Tests: `src/__tests__/rls/*.test.ts` run on PGlite via `src/testing/pglite.ts` (`createTestDb()` applies all migrations, creates a stub `auth.uid()` reading `request.jwt.claims`, and exposes `asUser(userId)`); `pnpm --filter @foundmill/db test:rls`.
- Seeds: `pnpm db:seed` builds Northwind Skincare and Ledgerly (BUILD §17.2) deterministically (seeded PRNG) and grants owner membership to `SEED_OWNER_EMAILS` (creating Supabase auth users through the admin API when `SUPABASE_SERVICE_ROLE_KEY` is set; on PGlite/test, users are plain rows in a stub `auth.users`).

## 5. Events (`packages/events`)

- `catalogue.ts` declares every event type from BUILD §8.1 with a Zod payload schema: `declareEvent("payment.received", schema)`. `EventType` is derived from the catalog. Unknown types fail at write time.
- `writeEvent(tx, { businessId, type, actor, entityIds, payload, occurredAt? })` inserts into `events` and `outbox` in the caller's transaction and returns the event id.
- `runOutboxRelay(db, redis, { batch, intervalMs })` publishes unpublished outbox rows to Redis Stream `ev:{businessId}` (XADD, fields `id`, `type`, `json`) and marks them published. Runs inside `apps/api` (one instance) for staging.
- `consume(redis, { businessId | "*" , group, consumer, handler })` wraps XREADGROUP with ack and dead-letter after 5 failures. Consumers (BUILD §8.1): composer, journey, source-watcher, metrics, health, playbooks.
- Agent session streams: `as:{sessionId}` with fields `kind` (tool_call, stdout, file_changed, test_result, phase_changed, progress, note) and `json`. `publishSessionEvent(redis, sessionId, event)`.

## 6. Models (`packages/models`)

- `MODELS` and `ROUTES` as BUILD §10.1 in `src/routing.ts`, plus `foundations` (Opus: a new business's vision, specification and roadmap, §19). `resolveModel(routeKey, override?)` applies lock/warn rules.
- `createModelClient({ mode, apiKey, onUsage })` → `client.complete({ route, system, messages, schema?, maxTokens?, cache? })`. With `schema` the result is parsed and validated (Zod) with one retry on invalid JSON. Mock mode: `src/mock/` returns deterministic responses keyed by route + a stable hash of the input, with handcrafted fixtures for composer, plan compiler, ideation, recommender, grader, coach, quarantined reader; unknown inputs fall back to a generic fixture per route.
- `RateLimiter` token buckets per key for requests/input/output tokens, refreshed from response headers; `429` → backoff with jitter for the affected session only. A call books `reserveTokens` output tokens (default `maxTokens`), so fan-out calls reserve an estimate rather than the cap.
- `meter(usage)` returns cost in minor units from `src/pricing.ts` (per model, per million tokens; prices are config, labeled estimates).
- Every call reaches `onUsage` once per API call, with the request's `attribution` and `billedTo`: `credits` for a client on the platform key (the default), `byok` for a client built with `billedTo: "byok"` on a business's own key. Sinks copy it into `usage_ledger.billed_to` through `bookUsage` (packages/db), never a literal. A live call stopped by its signal after the request went out is still reported: the prompt's estimated input tokens and no output, with `aborted: true` on the event (the ledger row keeps it in `details`); a call stopped before it was sent reports nothing.
- Per-route `effort` and `speed` live in `ROUTES` next to the model: first-draft routes (`ideation`, `ideationSlate`, `logoDesigner`, `foundations`, `foundationsSkeleton`) run Opus at effort `low`, and ask for fast mode, which is honored only with `MODEL_FAST_MODE=1` (beta endpoint and header, 2× price, its own limiter bucket, standard speed on a 429). A request's own `effort` wins; Haiku 4.5 gets none. The `conversation` route (a reply at an agent's desk) runs Opus at effort `low` without fast mode; its caller (`buildConversationRequest` in packages/agents) caps `max_tokens` at 3,000 (a reply is about 700 tokens, which is what the limiter books; Opus 5.5 always thinks and thinking counts toward `max_tokens`) and caches the system blocks (house rules + instructions, then the conversation rules).
- Streaming: `streamStructured(client, { route, system, messages, schema, elementPath, elementSchema, onElement, onPartial, signal })` streams the JSON (`messages.stream()`), validates each element of the array at `elementPath` as soon as it closes and hands it to `onElement`; the whole document is still validated at the end, repairing only the failed elements where it can. Delivered elements are never replaced. The mock client streams its deterministic fixture, paced by `MOCK_MODEL_LATENCY_MS` / `MOCK_MODEL_STREAM_MS` (both 0 by default, and forced to 0 by `loadEnv` outside `APP_ENV` development/test, like `DEV_AUTH_USER_ID`).

## 7. Policy (`packages/policy`)

- Cedar schema with entities `Agent`, `Tool`, `Business`, action `call`, and the context attributes from BUILD §9.5.
- `policies/*.cedar` with the hard-gate, suppression/untrusted-recipient, augmented-ask, assisted-caps and automated rules. `@outcome("ask")` annotations are read by the evaluator.
- `evaluate({ principal: AgentCtx, tool: ToolCtx, business: BusinessCtx, context })` → `{ outcome: "allow" | "ask" | "deny", reasons: string[], policyIds: string[] }`. Deny beats ask beats allow.
- Tests: every rule × every business mode, and "no Finance tool has a payment-initiation capability".

## 8. Connectors (`packages/connectors`)

- Contract exactly BUILD §13.1. `registry.get(key)` returns the real connector or `connector.mock` depending on `INTEGRATIONS_MODE`.
- Each connector folder: `index.ts` (real), `mock.ts`, `tools.ts` (tool definitions + policyHints), `webhooks.ts`, `fixtures/`, `*.test.ts` (contract tests against fixtures).
- Mock connectors are deterministic and can `simulate(eventName, params)` to emit platform events (used by the dev-only Simulate panel and by tests).

## 9. Gateway (`apps/gateway`)

HTTP (JSON), service-to-service auth with `SESSION_TOKEN_SECRET`-signed JWTs (`jose`):

- `POST /v1/session-tokens` (service auth) `{ businessId, agentId, sessionId, allowedTools, ttlSeconds, untrusted? }` → `{ token }`. `untrusted` (`{ emails, urls, phones, all }`) seeds the session's "first seen in untrusted content" register from the start: the orchestrator sends the recipients found in a code task's restored files. `LIVE_CONNECTORS` names connectors that run live while `INTEGRATIONS_MODE` is mock (GitHub first); an App connector (GitHub) runs live without a stored secret once the business's installation is connected **and verified**: status connected or degraded, and its installation id equal to the one the gateway recorded in `app_installations` (0015, written only by the gateway after checking with GitHub that the person connecting owns the account or administers the organization). `commit_files` is further held to the repository chosen on Development › Code, while pushing is on, with `[skip ci]`.
- `POST /v1/integrations/connect` and `POST /v1/integrations/health` (service auth, App connectors only) `{ businessId, connector, input? }` → `{ mode, record }` / `{ health }`. App connectors' keys (the GitHub App's private key and OAuth client) live only in the gateway, so the api connects and health-checks GitHub through these; GitHub's connect verifies the installer with the OAuth code before it returns a connected record. Bodies are limited per route (16 MB `/v1/call`, 4 MB `/mcp`, 1 MB service routes).
- `POST /v1/call` (Bearer session token) `{ connector, tool, args, context? }` → `{ outcome, result?, approvalId?, costMinor, auditId }`. Pipeline: authenticate → load connector → Cedar → if `ask` create `approvals` row + `approval.requested` event and return `outcome: "ask"` → if `allow` inject credential (decrypted in memory) → call → meter → audit → return.
- `GET /v1/connectors` → catalog with phase, auth kind, tools, policyHints.
- `ALL /mcp/:connector` streamable-HTTP MCP server exposing that connector's tools to the Claude Agent SDK; same pipeline.
- Rate limit per connector per business (Redis). All third-party content returned to agents is wrapped `{ untrusted: true, content }`.

## 10. Orchestrator (`apps/orchestrator`)

- Temporal worker on task queue `TEMPORAL_TASK_QUEUE`. Workflows in `src/workflows/*.ts` (pure, bundled), activities in `src/activities/*.ts`. A second worker in the same process serves `${TEMPORAL_TASK_QUEUE}-sessions` with the session run activity (`runAgentSession`) only, `ORCHESTRATOR_MAX_SESSIONS` at a time, so long or waiting sessions never take a slot from cycles, plans, imports, training, vacations or the control activities that reach sessions (`ORCHESTRATOR_MAX_ACTIVITIES`). When one worker stops the other is shut down, and a promise rejection nobody handled is logged rather than ending the process.
- `businessCycle(businessId)`: load brief → Chief of Staff plan (models) → dispatch `agentSession` children per task within concurrency/budget/rate capacity → collect → composer narrate → write `cycle.completed` → stop at time box.
- `agentSession(agentId, taskId)`: mints a gateway session token, runs the Claude Agent SDK (live) or the recorded replay (mock, in a `packages/sandbox` replay sandbox), streams to `as:{sessionId}`, writes `usage_ledger`, heartbeats, loop detection, pauses on `approval` signal. A live session creates a sandbox only for a code task's acceptance run (30 minutes, inside E2B Hobby's cap). Waiting for the founder is bounded: a gated call left undecided for `APPROVAL_WAIT_MINUTES` ends the session `blocked` (reason `awaiting_approval`, usage booked, the approval stays open), and a session paused for `SESSION_PAUSE_HOLD_MINUTES` parks (its run saves the work and returns; the workflow waits for Resume without a slot and starts the next run where the last stopped, a replay from its `<recording>@<index>` cursor). Pause interrupts the live SDK turn and holds every tool call until Resume; Stop, a loop and a cancel interrupt the turn and book its usage (the latest cumulative `result.modelUsage`, plus an Estimate from the assistant messages of a turn cut short). An API refusal the SDK reports as `is_error` blocks the session (`budget`, `credential` or `rate_limit`) instead of ending it `done`. A session never un-pauses its agent, and a stopped session of a paused agent leaves its task `paused`. Code tasks start from the task's latest saved workspace (restored before the session token is minted, so its recipients are untrusted from the first call) and save it again when the session ends, without secret files, credential values or start-up files (`workspace_snapshots` / `workspace_blobs`, written by the orchestrator only; read on Development › Code; owners and admins may forget a task's code). Each save is then pushed to the task's branch `agent/<taskId>` on the business's chosen repository with the GitHub connector's `commit_files`, through the gateway with a token for that one tool; the result is recorded on the save.
- Keys (BUILD §10.2): `deps.models` is `createBusinessModelClient` (`src/models.ts`) over the platform client. A call whose `attribution.businessId` names a business on its own key (`model_billing = byok`) runs on that key, decrypted here through `loadByokApiKey` (packages/db), cached per key for 30 s and booked as `byok`; in live mode a business on its own key with no readable key is refused (`missing_api_key`), never run on the platform's credits; in mock mode it gets a mock client that books to `byok`. Sessions resolve the same key for the Agent SDK and are blocked with reason `credential` when it is missing.
- Signals: `decision`, `shout`, `pause`, `resume`, `stop`, `founderSubmit`, `wake`. Queries: `progress`.
- `apps/api` starts workflows through `@temporalio/client`; workflow ids are deterministic: `cycle:{businessId}:{n}`, `session:{sessionId}`, `engine:{channelId}`, `holiday:{holidayId}`, `foundations:{businessId}:{attempt}`.
- When `TEMPORAL_ADDRESS` is unreachable in development, `pnpm dev` prints how to start `temporal server start-dev`.

## 11. Composer (`apps/composer`)

- `POST /v1/narrate` `{ businessId, eventIds }` → writes one `inbox_items` row (schema BUILD §11.3, validated with Zod, links validated by entity-linker, one re-ask on invalid ids) and returns it.
- `POST /v1/refresh` `{ businessId }` → exactly one new item from the buffer (priority: un-narrated event → data-change insight → next-best decision); refills the 3-item buffer asynchronously; debounced 3 s per business; p95 < 400 ms warm.
- `POST /v1/commentary` `{ journeyId }` → commentary lines for a Customer Update. `POST /v1/chapter-title` for quarters.

## 12. Stream (`apps/stream`)

WebSocket at `/?token=<supabase access token | dev token>`. Client → server: `{ "t": "sub", "ch": "ev:<businessId>" | "as:<sessionId>" }`, `{ "t": "unsub", "ch": ... }`, `{ "t": "ping" }`. Server → client: `{ "ch": "...", "e": <event json> }`, `{ "t": "pong" }`. Membership is checked per subscription. Per-channel throttling to 4 messages/s for unfocused tiles is done client-side; the server coalesces bursts to 20/s per socket.

## 13. API (`apps/api`)

- Hono app; `/trpc/*` via `@hono/trpc-server`; `/health`; `/webhooks/*` is **not** here (that is `apps/ingest`). tRPC answers are gzip-compressed (Hono `compress`) except streamed ones (`trpc-accept: application/jsonl`, Server-Sent Events), which pass through untouched.
- On boot, before listening: run the drizzle migrator over `DATABASE_URL` in one transaction under `pg_advisory_xact_lock(7461, 1)` (idempotent, safe with several replicas and on Supabase's transaction pooler; the lock cannot outlive the run), waiting at most `MIGRATION_LOCK_TIMEOUT_MS` for the lock and exiting 1 past it so the platform restarts the boot; then, if `SEED_ON_BOOT=1` and the demo businesses are absent, run the seed. Log and keep serving if the database is unreachable (health reports it). On SIGTERM every service drains within `SHUTDOWN_TIMEOUT_MS` and exits 0 (`@foundmill/shared/shutdown`; docs/DEPLOY.md §3).
- Context: `{ db, redis, temporal, userId, email, log }`. `protectedProcedure` requires a user; `businessProcedure` takes `{ businessId }` in input, asserts membership (and section permission where given) and provides `ctx.rls(fn)` = `withRls(db, { userId }, fn)`. The membership and the business are looked up in parallel, once per HTTP request and user for the whole batch (`ctx.accessMemo`, a new map for every request, never shared); the in-process caller and tests look up on every call.
- Model usage: the API's model client (`createApiModelClient`, `services/models.ts`) books every call whose `attribution.businessId` is set to that business's `usage_ledger`, one row per call (tokens, list price in USD, labeled Estimate, `details.service: "api"`), as the orchestrator's `usageSink` does: conversation replies, plan compiles, foundations run in-process, logo sets, recommenders, the in-process composer. Calls with no business (Ideation drafting, Ask on a concept, a logo before commit) are not booked. Callers never book model calls themselves.
- Routers named exactly as BUILD §8.3 (`founder.profile.get`, `inbox.list`, …) in `src/routers/<area>.ts`, merged in `src/router.ts`; `export type AppRouter`. Every mutation: Zod input, membership + permission, `audit`, `writeEvent` where relevant.
- JWT verification: `jose` against `${SUPABASE_URL}/auth/v1/.well-known/jwks.json` (cached). `DEV_AUTH_USER_ID` bypass only when `APP_ENV` is development/test.
- Logos: `business.logo.{get,prepare,upload,generate,remove}` (owner/admin writes, audited) and `idea.logo.{prepare,generate}` before commit; `idea.commit` takes the chosen logo. Clients send a `data:` URL; `checkLogo` (`@foundmill/shared/logo`: raster magic bytes, size and dimensions, the strict SVG sanitizer) is the only gate, run once per request: `repos.logos.set` stores a result `checkLogo` returned (frozen and registered, `isCheckedLogo`; a look-alike object is refused) or checks raw input itself before writing `business_logos` (0017, service-written, read by members). `business.get` carries the logo's metadata only (`logo.sha256`); the image comes from `business.logo.get`, cached by that version. Renderers draw a logo only as `<img src>` of a value `isLogoDataUrl` accepts (the design system's `BusinessLogo`). Generation (`logoDesigner` route, Opus) is metered as an Estimate and limited per user and per business (`LIMITS.logoSets*`); upload checks are limited per user (`LIMITS.logoChecksPerUserPerHour`). Both limits are in process.
- Conversations (the agent's desk): `agent.conversation.{get,send,handOff,inboxReply}` over `agent_threads` / `agent_messages` (0020, the Inbox's access model; Inbox subjects need the Inbox section, agents and tasks the Team section). `get` is deterministic (persona, presence, voice, starters); `send` calls the `conversation` route outside any transaction, re-checks the reply (`finaliseAgentReply` with `finaliseOptionsFor`: manifest mentions, hard gates → hand-off, 2–4 quick replies, a `choose_option` chip always named after the option it decides, and no quick reply or hand-off that repeats what only the subject's untrusted text said) and writes both messages with two `conversation.message_posted` events (never narrated) in one transaction; "Go with: …" goes through `decideInboxItem`; a hand-off is only staged (once per message) as a `pending_confirmation` plan and runs through `plan.confirm`. Only an instruction decides an Inbox item from free text: `inbox.decide` refuses a question, greeting, thanks or "not now", and `inboxReply` sends them to the conversation. A concept card (Ask) is built by `conceptConversationInput`: its title, pitch and evidence travel as untrusted data and never reach the system prompt.

- Preferences: `founder.preferences.{get,update}` (`protectedProcedure`, any signed-in account, with or without a business or a profile) read and change the caller's own `account_preferences` row (0022) as that user under RLS; `get` answers the defaults (`{ date: "us", time: "12h" }`) without writing a row; `update` takes `{ date?, time? }` (at least one, Zod-checked, nothing else) and returns the result. No event or audit row: both are business-scoped and the choice belongs to the account (§20).

## 14. Web (`apps/web`)

- `app/layout.tsx` loads `@foundmill/dugout/fonts.css`, `tokens.css`, `dugout.css` and `app/globals.css` (`@import "tailwindcss"; @source "../../../packages/dugout/src"; @source "../../../packages/widgets/src"; @source "../../../packages/modules/src";`).
- Routes exactly BUILD §6.2. `app/b/[bid]/layout.tsx` renders `AppShell` with sidebar from `department.list`, brand colors from `business.get`, and the Continue state from `inbox.list` + the current cycle.
- `lib/trpc.ts` (`@trpc/tanstack-react-query` with superjson, `NEXT_PUBLIC_API_URL`, Bearer from Supabase session; a `splitLink` sends the procedures listed in `STREAMING_PROCEDURES`, async generators on the api such as `idea.draft`, over `httpBatchStreamLink` and everything else over `httpBatchLink`), `lib/supabase/client.ts` + `server.ts` (`@supabase/ssr`), `lib/stream.ts` (one WebSocket per tab, subscription multiplexer, focus-aware throttling), `lib/keys.ts` (keyboard map from BUILD §5.5 with `react-hotkeys-hook`).
- Department screens: `app/b/[bid]/d/[deptSlug]/[tabSlug]/page.tsx` loads the `screen_definition` and renders `WidgetGrid` with widgets from `@foundmill/widgets`; module full-screen widgets come from `@foundmill/modules` (`getModuleScreen(moduleKey, tabSlug)` from `@foundmill/modules/registry`). The page loads only the module packs it shows (`useModulePacks` from `@foundmill/modules/lazy`: the tab's pack gates the screen, the department's other packs load alongside), and a widget layout (`components/screen/WidgetScreen.tsx`) is its own chunk.
- Bundles: `packages/dugout` declares `"sideEffects": ["**/*.css"]` and `packages/shared` and `packages/config` declare `false`, so a page ships only the design-system code it uses; a module that must run when imported (a registry) does not belong in them. Department icons and widget icons resolve through the curated map in `lib/icons.ts` (add an icon there when data names a new one). The Supabase browser client (only where Supabase is configured) and the Markdown parser are their own chunks, fetched once the page runs rather than with it. The agent desk sheet (`components/conversation/DeskHost.tsx`) is its own chunk too: fetched when a Talk / Ask control is pointed at or focused or the palette opens (`useAgentDesk().prefetch`), when the browser is idle after load, and at the latest on the first open; a page that imports `AgentConversation` itself (the Inbox's inline desk) hands its copy over instead. A Panel's "…" menu (Radix) loads only when a panel has one (`PanelMenuButton`), and the not-found files render the brand page through `LazyBrandPage`, because every page's payload carries its layouts' not-found trees.
- The LIVE pages (`/network`, `/communities[/id]`, `/leaderboards[/boardId]`, BUILD §6.2) are about the founder, not one business, so they live in the route group `app/(live)/`. Its layout loads the founder profile, picks the current business (`lib/auth/current-business.ts`: the `fm_last_business` cookie the business layout sets, else the newest business; none → `/new`) and renders the same `BusinessShell`, plus a `LiveViewerProvider` (who is signed in). ## 16. Rules for parallel build agents

1. **Own your directory.** Edit only the package/app you were assigned plus `docs/PROGRESS.md` (your rows) and `docs/DECISIONS.md` (append only). Never touch root files, `pnpm-workspace.yaml`, `pnpm-lock.yaml`, or another package.
2. **No installs, no new dependencies.** Everything you need is already installed (see the catalog in `pnpm-workspace.yaml`). If something essential is missing, append a line to `docs/NEEDED_DEPS.md` (`package — version — why — who`) and write the smallest local substitute so your package still typechecks.
3. **Check your work**: `pnpm --filter @foundmill/<name> typecheck`, `lint`, `test`. Fix every error in your package before you finish.
4. **No long-running servers on fixed ports** during the build phase (other agents share the machine). If you must boot something, use an ephemeral `PORT=0`/random port and stop it.
5. **Fetch current docs** before using an SDK (Temporal, Claude Agent SDK, Anthropic, Drizzle RLS, Tailwind v4, Storybook 10, react-grid-layout 2, TanStack Table 8, visx, PixiJS 8, xterm 6, Tiptap 3). Versions in the catalog are the truth.
6. **Mock first.** Everything must work with `INTEGRATIONS_MODE=mock` and `MODEL_MODE=mock`. Live paths are implemented but never required for tests.
7. **Design discipline.** UI follows `docs/DESIGN.md`. Tokens only, design-system components (`packages/dugout`) only, Lucide only, desktop only.
8. **Do not commit.** The orchestrating session commits between waves.
9. **Report** at the end: what exists, what is stubbed, commands that pass, and anything another package must know (exported names changed, contracts added).

## 18. Widget and module data contract

`packages/widgets` and `packages/modules` never import the tRPC client or the Next.js router. They read data through `WidgetDataSource` (packages/widgets/src/data.tsx): `useWidgetQuery(path, input)` for tRPC queries by dotted path (e.g. `"inbox.list"`), `mutate(path, input)`, `navigate(href)`, `subscribe(channel, handler)`, `businessId`, `glossary`, and the optional hook `useStreamOpen()` (read through `useHostStreamOpen()`: true while the host's event stream is connected, so a screen can poll less). `apps/web` wraps every business page in `<WidgetDataProvider source={…}>` with an implementation backed by its tRPC client, router and stream client. Widgets register with `registerWidget({ key, title, defaultSize, settingsSchema, Component })`; module screens register with `registerModule({ key, screens })` and are looked up by `getModuleScreen(moduleKey, tabSlug)`. The `@foundmill/widgets` barrel registers every widget and the `@foundmill/modules` barrel loads all six module packs, so code that needs only a helper imports its subpath: `@foundmill/widgets/data`, `/shared/routes`, `/shared/departments`, `/shared/time`, `/shared/types`; `@foundmill/modules/registry`, `/lazy`, `/product/foundations`. Screen definitions (`screen_definitions.layout`) reference widgets by key and module screens as `module:<moduleKey>/<tabSlug>`.

## 19. Foundations on the first open

A new business gets its vision, first specification and first roadmap when it is first opened (BUILD §11.1, §11.5).

- **State.** `business_foundations` (migration 0018, one row per business, read-only policy: services write, members read): `pending` at commit → `drafting` (claimed, `attempt` + 1) → `ready` or `failed`. The vision is stored on the row (`vision`); the specification goes to `spec_blocks` and the roadmap to `roadmap_items`, both through `repos.product`. While drafting, `progress` (migration 0019, jsonb on the same row, same policies) holds what has been written so far (`FoundationsProgress`: the vision, the plan's theses and roadmap titles, each finished section, the roadmap items), already plain text with figures labeled; it survives a failed attempt (Try again resumes from it) and `apply` clears it. `repos.foundations` owns the lifecycle: `create`, `claim(from)`, `setRunner`, `writeProgress` (atomic jsonb merge for the current attempt; one section at a time so parallel batches never overwrite each other; its `foundations.progressed` event in the same transaction), `fail`, `inputs`, `author`, `apply`. `apply` and `fail` act only for the current drafting attempt, and `apply` never writes a pinned block or one someone already wrote (the write is conditional on the version it read as empty). The Inbox note and its `inbox.item_created` event (`onInboxItem`) and the `foundations.progressed` "ready" event (`onApplied`) are written in the same transaction.
- **Inputs.** Door A (Ideation Studio): the committed idea (title, summary, archetype, the ten attributes with evidence, citations, Q&A) and the founder profile of the business's creator. Door B (Import): the same plus the Import report snapshotted on the row at commit and the imported sources commit stored as `sources` (`relevance.import`, only `http(s)` URIs). The link is the Import job id, an HMAC-signed token (`SESSION_TOKEN_SECRET` under the label `foundmill/import-job/v1`; a per-process key in development and test) that names the account that started it: `idea.generate({ importJobId })` records it on the idea Import drafts; commit reads it back, verifies it again (signed, this founder, a finished sign-up job with no business, sources that pass the same validation as `import.start`) and rebuilds the job (deterministic in its token).
- **Trigger.** The business shell calls `product.foundations.ensure` on load while `business.get` reports the foundations `pending` or `drafting` (`foundationsStatus`; never once they are ready, failed or absent) (any member; idempotent: one conditional claim, made only by a member with product write, so a viewer opening first leaves it pending; it returns only the status, door, attempt and times). It starts `businessFoundations` (`foundations:{businessId}:{attempt}`); when Temporal does not answer, apps/api runs the same steps in-process in the background (`runner: local`), at most two at once per process, each aborted after 8 minutes, waiting included, and booked to the usage ledger. On Temporal each drafting activity heartbeats and passes its cancellation signal to its model calls, so a timed-out attempt stops before the retry. An attempt older than 10 minutes (local) or 45 minutes (Temporal) counts as interrupted and becomes `failed`; the UI stops polling it and offers Try again. `product.foundations.retry` (product write) re-claims a failed one. `product.foundations.get` (product read) returns the state, the vision (while drafting as soon as it is written), the progress (`FoundationsProgressView`: stage, author, each section with its thesis or its text, the roadmap items written and planned) and a summary.
- **Drafting (staged, audit P3).** `packages/agents` foundations-staged (pure) and foundations-steps (calls the client it is given; not re-exported from the package root). Every call shares one system prefix, sent with a cache breakpoint: the house rules and the Product lead's instructions, then the `foundations_brief` prompt with the trusted inputs as JSON (`<`, `>` and backticks escaped). The user turn carries the untrusted inputs (model-written text: the idea card's title, summary and evidence, text already in the outline; research; imported content), each inside `<untrusted_content>`, then, for steps 2 and 3, the plan (model-written, so inside `<untrusted_content kind="plan">`), then the step's instruction. Step 1, `foundationsSkeleton` route (`FoundationsSkeletonOutput`): the vision, one thesis per outline section, the roadmap's titles; streamed, the vision is stored the moment it is complete. Step 2, `foundations` route, in parallel batches of two (three for a long outline, at most six calls): the named sections (`write_sections`), each stored as it streams; a batch that fails or leaves one out is followed by one call per missing section. Step 3, `foundations` route, in parallel with step 2: the roadmap items (stored as they stream) and the open questions. Output is bounded per call and the limiter books an estimate (`reserveTokens`). Each stored part is finalized on the way in (`finaliseVision`, `finaliseSection`: plain text, a heading first, figures not in the founder's inputs labeled Estimate or Forecast); `assembleFoundationsDraft` turns the stored progress into the same `FoundationsDraft` the single call made (`finaliseFoundations` stays for the evals: placeholders for missing sections, block links, every Import seed on the roadmap via `finaliseRoadmap`, every model and import string made plain text) → `repos.foundations.apply` → the Product lead's Inbox update (model values escaped for Markdown) and `inbox.item_created`. The in-process run is `draftFoundationsStaged` (the first failure aborts the other calls). The orchestrator runs one activity per step, each retried on its own (behind `patched("foundations-staged")`: a workflow started before the staged drafting replays on its old single-call path, `draftFoundations` → `applyFoundations` with the draft, which stay registered for one release): `draftFoundationsPlan` (returns the batches), `draftFoundationsSections` × batches and `draftFoundationsRoadmap` at once (a retry only redrafts what is not stored), then `applyFoundations` (assembles from the row) or `failFoundations`; the drafting activities fail only with `FoundationsDraftError`, whose fixed message is the only failure text the founder sees.
- **UI.** The design system's `FoundationsStatus` (in `packages/dugout`) until something is written, then `packages/modules` `FoundationsProgressPanel` ("Mira, Product lead, is writing the specification", "4 of 11 sections · 3 of 9 roadmap items", each section as it lands, with its text on the Specification tab, the vision statement on Home, the roadmap items arriving on Home and the Roadmap tab); `useFoundations` refreshes while pending or drafting (the shell refetches `product.foundations` on `foundations.progressed`, `INVALIDATE_ON_EVENT`; the screens poll every second when the host's `WidgetDataSource.useStreamOpen` says the stream is not connected, every 10 s when it is) and calls back when it turns ready; `FoundationsBanner` on Home and the Vision, Specification and Roadmap tabs; the Vision tab shows the vision as soon as it is written and reads a narrative section's drafted text (marked Drafting) while its block is still empty; `VisionPanels` on the Vision tab, and the spec narrative there rendered as plain text (`PlainDoc`: no images, links or entity mentions).

## 20. Date and time formats (Settings › Preferences)

The founder's rule (2026-10-11): every signed-in person chooses how dates and times read, for themselves, in every business and on every signed-in screen. US dates and 12-hour times stay the default and what the signed-out pages show. The patterns of each choice, and the table of them, are in docs/DECISIONS.md ("Date formats a person can choose"). Numbers and money do not change (en-US, each business's own currency).

**Storage and API.** `account_preferences` (migration 0022, one row per account, `user_id` unique, `date_format` in `us | day_first | iso`, `time_format` in `12h | 24h`, RLS `user_id = auth.uid()` for select, insert and update; no delete grant). `repos.preferences.get(db, userId)` (the defaults when there is no row) and `.update(db, userId, { date?, time? })` (upsert of what was given). `founder.preferences.get` / `founder.preferences.update` (§13). The enums are `DATE_FORMAT_PREFERENCES`, `TIME_FORMAT_PREFERENCES`, `DateFormatPrefs` and `DEFAULT_DATE_FORMAT_PREFS` in `@foundmill/shared` (Zod: `DateFormatPrefs`, `DateFormatPreference`, `TimeFormatPreference`).

**Rendering without a flash or a hydration mismatch.** The browser keeps a copy of the choice in the cookie `fm_date_format` (`<date>.<time>.<owner>`, the owner being the user id, or `dev` under the development sign-in; `lib/date-format.ts`). `getServerDateFormat()` (`apps/web/lib/date-format.server.ts`, React `cache()`d) reads it for the signed-in user and asks `founder.preferences.get` only when it is missing, malformed or someone else's. `DateFormatHost` starts from that value, checks it once against the account, rewrites the cookie whenever what it read or saved differs, and saves changes (`useDatePreferences().save({ date })`: optimistic, rolled back on failure; overlapping saves end on what was stored). Sign-out clears the cookie. The host renders the design system's `DateFormatProvider`.

**The API for call sites** (what the remaining migration uses; `@foundmill/dugout` unless noted):

| Where the date is printed | Use |
| --- | --- |
| A client component (design system, widgets, modules, apps/web) | `const { formatDate, formatDateShort, formatMonthYear, formatTime, formatDateTime, formatRange, formatHourOfDay, formatDateYearParts, prefs } = useFormatters()`. `formatDate(d, "weekdayDate")` takes a form's name or its US pattern (`DATE_FORMATS.weekdayDate`); `formatRange(a, b, { withYear })`. |
| A pure helper or a memo outside React | Take `prefs` (from `useDateFormat()` in the caller) and pass it on: `formatDate(d, "dayMonth", prefs)`, `formatDateTime(d, prefs)`, `formatTime(d, prefs)`, `formatDateShort(d, prefs)`, `formatMonthYear(d, prefs)`, `formatDateRange(a, b, { withYear, prefs })`, `formatHourOfDay(h, prefs)`, `formatDateYearParts(d, prefs)`, or `bindFormatters(prefs)` for all of them. Without `prefs` every helper reads US and 12-hour. |
| A chart or library that takes a date-fns pattern | `datePatternFor("dayMonth", prefs)` (forms: `date`, `dayMonth`, `weekdayDayMonth`, `weekdayDate`, `longDate`, `monthYear`, `time`, `timeSeconds`, `dateTime`, `dayMonthTime`). |
| A server component, or a server-safe design-system component (`SERVER_SAFE_FILES`) | No hooks: take the choice as a prop and call `bindFormatters(prefs)`. The design system's server-safe components that print a date take it as `datePrefs?: DateFormatPrefs | null` (`DevelopmentChart`, `FeedPost`, `ReadReceipt`, `LiveRun`); a client caller passes `datePrefs={useDateFormat()}`, and without it they read US and 12-hour. |
| apps/web's UTC helpers (`apps/web/lib/format.ts`, settings and CRM copy) | `formatDate(v, prefs)`, `formatDayMonth(v, prefs)`, `formatMonthYear(v, { long }, prefs)`, `formatDateTime(v, prefs)` (still UTC, still "UTC" after a time). |
| A test or a story in another format | Wrap it in `<DateFormatProvider value={{ date: "day_first", time: "24h" }}>`. |

Rules for each call site:

1. Replace a literal pattern with the form's name (`formatDate(d, "MMM d")` → `formatDateShort(d)`); never spell a day-first, ISO or 24-hour pattern (the US English guard allows them only in `lib/date-preferences.ts`). A pattern that is not a form (`"yyyy"`, `"EEE"`, `"MMM"`) prints as written in every choice.
2. Leave alone: relative times (`formatRelative`: "3 min ago"), dates written inside agent prose and other stored text, machine formats (day keys such as `2026-10-07`, ISO strings on the wire, a `<time dateTime>` attribute, file exports), and numbers and money.
3. The provider makes the *format* the same on the server and in the browser; it does not make the *time zone* the same (the server renders in UTC). An absolute local time in server-rendered markup renders only once hydrated (`useHydrated()`, `useClientToday()`, `useClientNow()` in `apps/web/lib/today.ts`) or prints in UTC through `apps/web/lib/format.ts`. A date-only string (`2026-10-07`) is read by the design system's helpers as that calendar day wherever the reader is.
4. A memo that formats must list the formatters (or `prefs`) in its dependencies, so a change of choice redraws it without a reload.
5. A component whose dates now follow the choice gets a test in a second format (a provider in its test) and keeps its US story.
