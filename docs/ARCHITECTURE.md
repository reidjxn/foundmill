# ARCHITECTURE.md — build contracts

How the repo fits together and the contracts each package exposes to the others. `docs/BUILD.md` is the product spec; this file is what you code against. Read `docs/DECISIONS.md` for choices already made and `docs/DESIGN.md` for the look.

## 1. Layout and ownership

```
apps/web           Next.js 16 App Router. Shell + every surface. Talks to apps/api over tRPC and to apps/stream over WebSocket.
apps/api           Hono + tRPC. Auth context (Supabase JWT), membership checks, RLS-scoped queries, audit, events. Starts Temporal workflows.
apps/gateway       The only process that holds vendor secrets. Session tokens, Cedar policy, connectors (real or mock), metering, audit. Also serves MCP endpoints.
apps/orchestrator  Temporal worker: businessCycle, autopilot, agentSession, approvalWait, channelEngine, trainingRun, holiday, playbook, incorporation, journeyBuild, importBusiness, businessFoundations, sourceWatch (+ sourceWatchSweep), postDraft, schedules.
apps/composer      Inbox Composer + Refresh buffer + Journey commentary + chapter titles. HTTP service called by api and orchestrator.
apps/ingest        Webhook receivers (Stripe, SendGrid, GitHub, Shopify, ...) → verified → normalised platform events via the outbox; the platform sending address's replies, delivery events and unsubscribe link (`/mail/*`).
apps/sites         Foundmill Sites (WP-07): serves each project's static site at `<slug>.<SITES_DOMAIN>` and release previews at `p-<token>.<SITES_DOMAIN>`, plus its own `/_fm/report`. Static only, no cookies, a strict header set, and a database login (`sites_reader`) that can execute the three site functions and read no table. Off while `SITES_DOMAIN` is unset.
apps/stream        WebSocket fan-out of Redis streams (ev:{businessId}, as:{sessionId}, u:{userId}, ae:{userId}) to browser tabs.
apps/collab        Hocuspocus (Yjs) server for spec blocks.
apps/social        LIVE network, communities (Phase 4; skeleton only now).
packages/config    APP_NAME, feature flags, pricing tiers, limits. No dependencies.
packages/shared    Vocabulary types/enums (src/constants.ts, src/types.ts), errors, Result, money, ids, env parsing; server-only subpaths /logger and /crypto (envelope encryption).
packages/dugout    Design system: tokens.css, fonts.css, dugout.css, every component, Storybook.
packages/db        Drizzle schema, SQL migrations, RLS, repos, seeds, PGlite test harness.
packages/events    Event catalogue (Zod; business-scoped and account-scoped types), outbox writers, Redis relays, consumer helpers.
packages/models    Model routing (the only place model ids live), Anthropic client with mock mode, rate-limit buckets, cost metering.
packages/agents    Agent templates, prompt templates (§12), skill definitions, calibration, archetype seeds.
packages/policy    Cedar schema + policies + evaluator wrapper + tests.
packages/connectors Connector contract, registry, one folder per connector with real + mock.
packages/entity-linker Manifest builder, [[ent:id|Name]] parser/validator, Haiku sweep, render helpers.
packages/journey   Attribution, xC model, journey builder, synthetic journey data generator.
packages/widgets   Widget registry (key → component, default size, settings schema, data hook) shared by Home and department screens.
packages/modules   Built-in module screens (product, development, distribution, finance, team, legal) registered by module key + tab slug.
packages/sandbox   Sandbox interface; E2B, local Docker, and mock (replay) runners.
evals/             Golden tasks and rubrics per agent template and skill.
e2e/               Playwright suites.
```

Package names are `@foundmill/<dir>`. Every package exports TypeScript source directly:

```json
"exports": { ".": "./src/index.ts", "./*.css": "./src/*.css", "./*": "./src/*.ts" }
```

So `@foundmill/db/repos` resolves to `packages/db/src/repos.ts` (a file that re-exports `./repos/index`). Subpath modules are files, not directories.

## 2. Vocabulary (`packages/shared/src/types.ts`)

Every enum used by more than one package is defined once here as a `const` tuple with a matching Zod enum and TS type: game modes, business modes, plan tiers, archetypes, module keys, membership roles, inbox item types/states, agent statuses, model keys, channel keys and lines, task kinds/statuses, plan action types, conversion kinds, Customer Update levels (`matchday_level`), entity kinds, skill groups, integration statuses, visibility, event types. Import from `@foundmill/shared`. Do not redeclare these elsewhere. The tuples, their TS types and the plain records built from them (`MODULE_TABS`, `CHANNEL_META`, `ARCHETYPE_LABELS`…) live in `src/constants.ts` without Zod, and browser code imports them from `@foundmill/shared/constants` so a page does not download Zod; the Zod enums stay in `src/types.ts` and the barrel exports both. Server-only code is not in the barrel: the pino logger is `@foundmill/shared/logger` and envelope encryption (libsodium, AWS KMS) is `@foundmill/shared/crypto`.

**Definitions and plain language** (UX plan §6.1, Oct 20, 2026): `packages/shared/src/terms.ts` (`@foundmill/shared/terms`) is the one definitions source the UI, the Composer and the plain-language linter share. `TERMS` (about 95 entries, `as const satisfies Record<string, TermDefinition>`) is keyed by a stable id, never by the display word: `{ id, word, short, long?, learn? }`, a short line of one sentence under 140 characters with units on numbers, a long of two or three sentences, and `learn` a slug in the display vocabulary (`finance/runway`, `team/agents`, `distribution/board`) that `learnPath(learn, businessId)` resolves to `/b/<id>/d/<dept>/<tab>`, `/b/<id>/settings/<tab>` or `/b/<id>/<page>` through `LEARN_SLUG_ALIASES` (the kept URL slugs `squad`, `formation`, `training-ground`, `wage-bill`). `termsWithGlossary(glossary)` runs the business's rename map (`applyGlossary`) over `word`, `short` and `long`, never over `id` or `learn`. `PLAIN_LANGUAGE_TIERS` is `{ replace, define }`: the 18 phrases a founder never reads (ICP, CPA, named query, exhibit, counterparty, …) and every display word of `TERMS`; `TERM_IDS` carries the ids. `terms.test.ts` holds every entry to the voice rules (US English, no sport words, no replace-tier word inside a definition, a real route behind every `learn`). The guided layer's enums sit beside the date-format ones in `src/constants.ts`: `GUIDANCE_MODES` (`on | off`) and `TEXT_SIZES` (`standard | comfortable`) with `GuidanceMode` / `TextSize`, re-exported by the db schema. `MEMBERSHIP_SOURCES` (`invite | founder | example`) is declared in `packages/db/src/schema/tenancy.ts` for now (moving it to `src/constants.ts` next to `MEMBERSHIP_ROLES` is a filed request).

**Team tiers** (Leads first, founder 2026-11-08): `packages/shared/src/team-tiers.ts` (`@foundmill/shared/team-tiers`, also in the barrel) is the one rule for who the founder sees. `agentTier(agent, leads)` returns `chief | lead | specialist | background` from what is stored, with no column of its own: the Chief of Staff (the assistant layer, or `chiefOfStaff` from the API), the background helpers (the utility layer or a template in `BACKGROUND_HELPER_AGENT_TYPES`, the five utilities; the Planner is a specialist), the leads (a department's `lead_agent_id`, the lead layer, a `*_lead` template), else a specialist. `teamTree(agents, departments)` gives the tiers, the Hierarchy's reporting line (`parentOf`: a live, visible line manager, else the first department's lead, else the Chief of Staff; the Chief of Staff reports to the founder, `null`; a helper is never a parent), the Agents tab's groups (the Chief of Staff, then leads in department order, each with the specialists whose line reaches it first) and the counts; `teamCaption` and `backgroundHelpersLine` are the founder's words. `team.agents.list` and `department.list` add each agent's `tier`; every founder list and count (Agents tab, Health, Hierarchy, department cards and team strip, the status strip's Team health, the palette's Ask rows, the pickers, Recruitment, Agent of the week) drops `background` through `isBackgroundAgent` / `founderVisible`, while the entity resolver and the persona roster keep every agent so old mentions resolve. `pickAssignee` never gives a task to the utility layer, `team.agents.catalogue` leaves the utility family out unless asked by name, and the composer's manifest (`apps/composer/src/context.ts`) leaves helpers out. The design system's DataTable (`packages/dugout`) nests rows for the Agents tab (`getSubRows`, `filterFromLeafRows`, an expander after the first cell, ArrowRight / ArrowLeft, `isPinnedRow`, a flat CSV with `exportColumns`).

Money is `{ amountMinor: number; currency: string }` (minor units, `bigint` in the DB, `number` in TS; values are below 2^53). Ids are UUID strings. Times are ISO strings on the wire and `Date` in TS.

## 3. Modes and environment

- `APP_ENV`: `development | test | staging | production`.
- `INTEGRATIONS_MODE`: `mock | live`. The connector registry returns `connector.mock` in mock mode. Default mock.
- `MODEL_MODE`: `mock | live`. `packages/models` returns recorded/deterministic completions in mock mode. Default mock. Evals always force live.
- Env is parsed once per process with Zod in `packages/shared/src/env.ts` (`loadEnv()`); never read `process.env` directly elsewhere. The web bundle only sees `NEXT_PUBLIC_*`.
- `NOTIFY_EMAIL`: `on | off` (default on; apps/api). The notify pass (§13) emails a person about a note that waits for their answer, at boot and every five minutes, only where `PLATFORM_MAIL_DOMAIN` is set; `off` stops it. `PLATFORM_NOTIFY_LOCAL_PART` (gateway, default `hello`, must be one of `MAIL_RESERVED_LOCAL_PARTS` so no project can hold it) is the local part that email comes from. `PLATFORM_SAFETY_DAILY_CEILING` (gateway, default 5,000) is the founder notices' own enforced daily ceiling (`pn:safety:day`), apart from `PLATFORM_NOTIFY_DAILY_CEILING`.
- `DEMO_ROLL_FORWARD`: `on | off` (default on; apps/api). The demo businesses' own sample rows (the ids the seed recorded in `demo_sample_rows`) move forward with the calendar at boot and every hour (`rollDemoForward`, DECISIONS 2026-11-10); `off` leaves them where the seed put them.
- Ports (dev): web 3000, api 4000, gateway 4001, composer 4002, stream 4003, collab 4004, ingest 4005, social 4006. Services read `PORT` first (Railway sets it) and fall back to their named port.

## 4. Database (`packages/db`)

- `createDb(url)` → Drizzle `Db` over postgres.js. `createServiceDb()` reads `DATABASE_URL`.
- `withRls(db, { userId, role?: "authenticated" }, fn)` runs `fn(tx)` inside a transaction after `set local role authenticated` and `set local request.jwt.claims = '{"sub": "<userId>", "role": "authenticated"}'`. `apps/api` uses this for every user-originated query so Postgres RLS enforces tenancy. On postgres.js the setup (one statement, both values bound parameters) is queued before `fn` runs and travels with the transaction's first statements instead of costing a round trip of its own.
- Service code (orchestrator, composer, ingest, gateway) uses the service role **through repositories only**: `repos.<area>.<fn>(db, businessId, ...)` with `businessId` as the required first argument after `db`. The ESLint rule `fm/no-raw-db` forbids `db.select/insert/update/delete/execute` outside `packages/db/src/repos/**`, migrations, seeds, tests and the events outbox.
- Repos live in `packages/db/src/repos/<area>.ts` and are re-exported from `src/repos.ts` as `repos`. Areas mirror BUILD §7.2 groups: `businesses`, `memberships`, `founders`, `ideas`, `product`, `departments`, `screens`, `dashboards`, `agents`, `skills`, `training`, `tasks`, `playbooks`, `holidays`, `inbox`, `plans`, `channels`, `campaigns`, `journeys`, `entities`, `finance`, `capTable`, `usage`, `legal`, `integrations`, `credentials`, `policies`, `approvals`, `audit`, `events`, `social`, `presence`, `notifications`, `notificationPrefs`, `notifyFacts` (the return loop, 0076: presence and visit days per person and business, founder emails and their dedupe keys, the email preferences on `account_preferences`, and the notifier's read-only facts), `preferences` (account-scoped: the signed-in person's date and time format, §20, and the guided layer's state below).

- **Account events** (founder, Nov 12, 2026; migration 0085, §4). An event is account-scoped when the fact is about a person and not about a project: their own profile went public or was taken down (`profile.published`, `profile.unpublished`: the first two, payload `{ handle }` and nothing else), a public page or profile brought them or brought someone through theirs (`signup.attributed`, `referral.arrived`: payload `{ sourceKind, sourceRef }` and nothing else; "The attribution events" below), and later a follow, an ask, an answer. Such a fact is never written to a business, where every member reads the event rows and the `ev:` stream. To add one, four things: (1) append the type to `EVENT_TYPES` and to `ACCOUNT_EVENT_TYPES` (packages/shared `constants.ts`); (2) a migration with `create or replace function fm_account_event_types()` returning the longer list (the database lets only the listed types into `account_events` and keeps them out of `events`; packages/db `rls/account-events.test.ts` fails until the two lists are the same); (3) declare it with `declareAccountEvent(type, schema, { doc, consumers, recordIds? })`; (4) add its fixture. No wall entry is needed.
  - **The two-person rule.** A fact about two people is one row per person it belongs to, each with a payload shaped for that reader. A payload names another person only by something already public about them (a public handle), never by account id, email address or any private field; the row's own account is the envelope's `userId`. It is held in four places: (1) at declaration, `assertAccountPayloadSchema` (`account-payload.ts`, run by `declareAccountEvent` as the catalog loads): a closed object of plain fields, no key that names a person by an account (`userId`, `fromUserId`, `followerId`, …) or carries a contact detail or a credential, a UUID field only when the declaration lists it under `recordIds` (the id of a record, never of an account), no email field, nothing free-form (`z.record`, `z.unknown`, a loose object); (2) at write, `assertAccountPayloadValues` and `assertAccountActor`: no value and no key carries the account id of anyone the fact is about (the row's person, the other rows of the same call, `otherAccountIds`), no email-shaped text, nothing shaped like an id outside `recordIds` (a declared record id holds one plain UUID), and the actor is exactly `{ kind, id }`: the person themselves or the system by a lowercase word; (3) in the database, whichever writer: `fm_account_events_guard` and `account_events_actor_own` (§4); (4) tests of each, with every spelling below.
  - **What is enforced, and what cannot be.** Enforced: any single value (or key) that carries an account id in any common spelling: with its hyphens, without them, with hyphens elsewhere, in capitals, with Unicode dashes, with spaces, dots, colons or underscores between its parts, in braces, behind a prefix, inside a sentence or a longer run of letters and digits. The writer also folds fullwidth characters and finds the id of anyone the fact is about through any separator at all; the database checks every account there is. Not enforceable by either: an id cut into pieces across several values (`{ a: "0a1b…", b: "…4e5f" }`), an id in another encoding (base64, a number), and private facts that are not ids. The schema conventions (closed objects, plain fields, declared record ids) are what stand against those, with review of each new declaration.
  - **Errors say which rule and how deep, never what.** A refusal at write (`AccountRuleError`, with `rule`) and a value that does not parse (`AccountEventParseError`, with `reason`; text from `issueReason`: issue codes and depths) never repeat a key or a value of the payload: Zod's own text for a strict object is `Unrecognized key: "<the key>"`, and a key can be an email address. That text is what reaches `account_outbox.last_error`, the relay's dead letter and the api's warn log.
  - **Writing.** `writeAccountEvent(tx, { userId, type, actor, payload, occurredAt?, id?, idempotencyKey?, otherAccountIds? })` (`outbox/account-writer.ts`) validates against the catalog and inserts into `account_events` and `account_outbox` in the caller's transaction; it returns the event id. `writeAccountEvents(tx, inputs)` writes one fact for several people (one row each, each person once; every input validated before the first insert). `idempotencyKey`: a repeat for the same person returns the first event's id and writes nothing, without failing the caller's transaction (`on conflict do nothing`). The compiler and a runtime check refuse a business-scoped type here and an account-scoped type in `writeEvent` / `buildEvent` / `repos.events.write`. `buildAccountEvent` validates without writing.
  - **Relay.** `runAccountOutboxRelay(db, redis, opts)` (`outbox/account-relay.ts`; `createAccountOutboxRelay` without starting) publishes unpublished queue rows to the Redis Stream `ae:{userId}` (`accountStreamKey`, lowercase; XADD fields `id`, `type`, `json` = the `AccountEvent` envelope `{ id, userId, type, occurredAt, actor, payload }`) and marks them published. It runs in apps/api beside the business relay (`superviseOutboxRelay` starts both once Redis answers, `wake()` wakes both, `stop()` stops both); each relay has its own loop (`outbox/relay-loop.ts`), transactions and backoff, so a stuck account outbox never holds up a project's events, and the reverse. Failure handling is on the row: a row whose XADD fails keeps `published_at` null, `attempts` goes up, `last_error` holds the error's name and message (300 characters; a Redis error's own words, or issue codes and depths for a row that does not parse; never a key or a value of the payload) and `next_attempt_at` moves out (2 s doubling to 5 minutes), while the other rows of the batch are still published; a row that can never be a valid account event is closed (`published_at` set, `last_error` kept) and noted on `dlq:account-outbox-relay` by id, type and reason, without its payload; when nothing in a batch got through, the tick fails and the loop backs off (1 s doubling to 30 s). At-least-once: consumers de-duplicate on the event `id`. **One loop since 2026-11-13** (apps/api `services/relay.ts`, `combineRelays`): the api's relay runs the business batch and then the account batch in each tick, so the pool carries one poller; an account failure never fails the tick; `stop()` waits at most `RELAY_STOP_TIMEOUT_MS` (5 s). It was off from Nov 12 to 13 while the pool problem was fixed (#91, #95).
  - **The stream key is `ae:{userId}`, not `u:{userId}`.** `u:` stays what it was: content-free LIVE signals written straight after a commit, best effort, capped at 200 entries, delivered raw. Account events carry payloads, come from an outbox at least once, are read by consumer groups and are trimmed by age, so they have a key of their own and `publishUserSignal`, `readUserSignal` and the `u:` channel are unchanged.
  - **Consuming.** `consumeAccountEvents(redis, { userId | "*", group, consumer, handler, types? })` is `consume` over the account streams with the same guarantees (consumer group, ack after the handler, retries, pending-claim, dead letter after 5 failures); the handler gets a typed `AccountEvent`, `types` narrows it and acknowledges the rest; an entry that is not a valid account event of the stream's own person is poison (`decodeAccountEntry`, `AccountEntryError`); a dead letter keeps a reason code (`no_json`, `invalid_json`, `wrong_account`, `invalid_envelope`, `unknown_type`, `business_scoped`, `invalid_payload`, `handler_failed`, `too_many_deliveries`), the event's id (only when it is a UUID) and its type (only when it is account-scoped), with `group`, `consumer`, `deliveries` and `failed_at`: not the payload, not the stream's name (it holds the person's account id) and not a handler's own error text (`accountDeadLetterRecord`, through `consume`'s `deadLetterRecord` option; the business consumer's dead letters are as before). `parseAccountEvent` / `safeParseAccountEvent` refuse a business-scoped type, as `parseEvent` refuses an account-scoped one.
  - **The wall.** apps/stream delivers `ae:<userId>` only to connections signed in as that account (§12); a person also reads their own rows through RLS (§4). Nobody else reads either: not another account, not a cofounder or collaborator in the same project, not a signed-out visitor.
  - **Lifecycle.** The rows go with the account (cascade from `auth.users`; nothing is kept). The relay trims each `ae:` stream it writes to 7 days and sets the same TTL (`ACCOUNT_STREAM_RETENTION_MS`), so the copy in Redis is gone within 7 days of the last event at the latest; `deleteAccountStream(redis, userId)` removes it at once, for the flow that deletes an account (no such flow exists in the api yet). Not in a business's export. Nothing is backfilled for facts that happened before 0085.
  - **The profile events and the address.** An address that is, or holds, something shaped like an id (32 letters a to f and digits in a row once the hyphens are out) is refused by the api when it is saved and when a profile goes public (`handleLooksLikeAnId`, the reserved-address sentence), and is never suggested. Taking a profile down never depends on its event: the event is built first and written in a savepoint, and if either fails the profile is taken down all the same and the event skipped (a warning with the account id and a reason code).
  - **The attribution events** (0088; apps/api `services/attribution.ts`, called by `onPersonCreated`, §13). One sign-up that a public address brought is a fact about two people, so it is two rows, written with `writeAccountEvents` in the transaction that inserts the `attributions` row, and only when that insert wrote a row (once per account; never for a reference that did not resolve, that named the person themselves, or that arrived a second time): `signup.attributed` in the new person's own account events ("you arrived through this public page or profile") and, when someone is credited, `referral.arrived` in theirs ("someone signed up through your page or profile"; the credited person is a project page's longest-standing owner or a profile's own person). Both payloads are `{ sourceKind, sourceRef }`: `project_page` or `person_profile`, and the slug or handle as it arrived (public: it was in an address). Neither carries an account id or the project's id; the new person's row does not say who is credited (a page need not name its founders), and the credited person's row says nothing about who signed up: no id, no handle, no name, no email address, no count and no time beyond the event's own. The `attributions` row, which only the services read, is the one place that holds the two accounts and the project together by id. The actor of both rows is the system by a word (`attribution`), so the new person is never the actor on the credited person's row. Both rows carry the attribution's own time as `occurredAt`. Idempotency keys are `attribution:<attributions.id>:signup` and `attribution:<attributions.id>:referral`: built from the row's own id and never from an account's, different from each other, and in a column no client role reads.
    - *What `referral.arrived` can still tell its reader.* The fact and its time. A person who gave their address to one person only learns that this person signed up, and when; that is what the event says and it cannot be taken out without not writing it. Nothing in the row lets the reader find the account. The exact time is what could later be matched with something the new person does in public (a profile that goes public minutes after). Nothing is built to blur it: rounding `occurredAt` would change nothing while `created_at` and live delivery on `ae:` say the same, and writing the row late and in groups is a pass of its own, to be decided with the credit for bringing people. The rule until then: nothing is added to this payload that narrows who it was.
    - *The row never depends on its events.* The row is what credit is later paid from and it can be written once only, so the two events go in a savepoint inside the row's transaction: both are written with the row, or the row is kept without them and the api warns with the new person's account id and a reason code (the rule refused, or `write_failed`), never the reference and never the credited person. The known case: an address shaped like an id (a slug of 32 letters a to f and digits) is refused in any account event. Because the keys come from the row's id, the events can be written from the rows later and a repeat writes nothing; no such pass exists yet.
- Retention (Redis runs `noeviction`; keys.ts): every session publish sets a 14-day TTL on `as:{sessionId}` as a backstop; `finishSession` copies the stream into `session_recordings` (0053, one row per session, entries with their stream ids, output past 8 MB cut and the row marked `truncated`) and leaves the stream an hour to live; `dev.sessions.replay` reads the saved copy first, then the stream, then the mock recording. The outbox relay trims each `ev:{businessId}` it writes to 30 days (XTRIM MINID, measured from the id Redis gave the newest entry) and sets the same TTL, so the stream of a business that stopped producing events goes too; archiving a business deletes it at once.

## 9. Gateway (`apps/gateway`)

HTTP (JSON), service-to-service auth with `SESSION_TOKEN_SECRET`-signed JWTs (`jose`):

- `POST /v1/session-tokens` (service auth) `{ businessId, agentId, sessionId, allowedTools, ttlSeconds, untrusted? }` → `{ token }`. `sessionId` must be an `agent_sessions` row of that agent (404 `session_not_found`, 403 `session_agent_mismatch`), or `null` for a call the platform makes for the business outside any agent session (a confirmed plan action, an import): its usage, approval and audit rows then carry no session. `untrusted` (`{ emails, urls, phones, all }`) seeds the session's "first seen in untrusted content" register from the start: the orchestrator sends the recipients found in a code task's restored files. `LIVE_CONNECTORS` names connectors that run live while `INTEGRATIONS_MODE` is mock (GitHub first); an App connector (GitHub) runs live without a stored secret once the business's installation is connected **and verified**: status connected or degraded, and its installation id equal to the one the gateway recorded in `app_installations` (0015, written only by the gateway after checking with GitHub that the person connecting owns the account or administers the organization). `commit_files` is further held to the repository chosen on Development › Code, while pushing is on, with `[skip ci]`.
- `POST /v1/integrations/connect` and `POST /v1/integrations/health` (service auth, `svc: api` only; every connector a business may connect, `integrations.ts`) `{ businessId, connector, input? }` → `{ mode, record, integrationId, credential }` / `{ health }`. Every vendor key (the GitHub App's private key and OAuth client, the Google, Notion and Shopify OAuth clients, Stripe, Plaid and Tink, the registries' keys) lives only in the gateway, so the api connects and health-checks every live integration through these (SEC-14). GitHub's connect verifies the installer with the OAuth code before it returns a connected record and records the verified installation. Any other connector's `connect()` runs here (a key the founder entered, an OAuth consent link or code exchange, a Plaid or Tink link); a secret the vendor hands back (`credentialToStore`, live only) is sealed with the gateway's vault under the row-bound AAD and stored under `INTEGRATION_CREDENTIAL_KIND` with its integration row in one transaction, and the answer carries the record without it, the row id and `credential: { stored, credentialId, hint }` (`redactSecret`, four characters), or `integrationId: null, credential: null` when nothing was written (a consent link). The api then writes the row's settings, `connectedBy` and its own `integrations.connect` audit row. Health runs `healthcheck()` on the stored row (a GitHub installation only when this gateway verified it). The Anthropic key (Settings › Keys), the service-only connectors and the built-ins are refused (400). ## 12. Stream (`apps/stream`)

WebSocket at `/`. The access token (Supabase access token or dev token) never travels in the URL, where proxies and CDNs log it: the client offers two subprotocols, `foundmill.stream.v1` and `foundmill.bearer.<base64url(token)>`; the server verifies the bearer before the upgrade (401 for a bad token, 403 for an account the api would not admit: not on the invite list and without an admission, `liveChannelAdmit`; never a socket), selects `foundmill.stream.v1` only (the token is not echoed) and answers `Cache-Control: no-store`; an upgrade that still carries `?token=` is refused with 400. A socket lives no longer than its token: at the token's `exp` the server closes it with 4001, so the client sends a fresh token on the open socket before then (`{ "t": "auth", "token": ... }`, answered by `{ "t": "authed", "exp": ... }`; a token for another account closes the socket). Client → server: `{ "t": "sub", "ch": "ev:<businessId>" | "as:<sessionId>" | "u:<userId>" | "ae:<userId>" }`, `{ "t": "unsub", "ch": ... }`, `{ "t": "ping" }`. Server → client: `{ "ch": "...", "e": <event json> }`, `{ "t": "pong" }`, `{ "t": "subscribed", "ch": ... }` once a subscription is live (again for a repeated `sub`), `{ "t": "err", "ch"?, "code", "message" }` when it is refused. Membership is checked per subscription (`u:<userId>`, the person's own LIVE signals in any business and mode, is open to that signed-in user only and carries no business data), with the same section walls as the API (security review S1): every event type is filed under the sections it belongs to (`apps/stream/src/walls.ts`, checked against `EVENT_TYPES` at compile time), so a reader walled from a section never receives its events (a member with Finance `none` gets no `payment.received`), and fields that quote another section are taken out for a reader walled from it (amounts and costs behind Finance, payers and free text behind the CRM; the event then carries `redacted: [...]`). `as:<sessionId>` needs read access to Development and to every module of the department the session's work is filed under (`sessionSections`, also enforced by `dev.sessions.*`). `ae:<userId>` (the person's own account events, §5) has a wall of its own: the subscription is open to the signed-in account whose id it names and to no other (the same comparison as `u:`; no membership, role or section opens it, so a cofounder in the same project is refused like a stranger, and a connection that is not signed in never gets a socket); every entry is then held to the channel's account before it is sent (`viewAccountEvent` in `walls.ts`: the event's `userId` is that account, its type is account-scoped and agrees with the entry's, and only `id, userId, type, occurredAt, payload` leave, the fields the person may also select from the table; anything else on the stream is dropped and counted in `events_walled_total`); and an account-scoped type that strays onto a business stream reaches no reader of it, walls or none, like a person-addressed one (it has no line in `EVENT_WALLS`, which files the business-scoped types). Access follows membership changes: `invitation.accept` and `team.humans.role/remove` write `membership.changed`, and the stream holds that person's subscriptions to the business, re-checks them and closes the ones they lost (`err` on the channel); all live subscriptions are also re-checked every 30 s. apps/collab re-authorizes its open connections every 15 s the same way (closed, or turned read-only). Per-channel throttling to 4 messages/s for unfocused tiles is done client-side; the server coalesces bursts to 20/s per socket. Readers start at the live tail (no replay): a tab treats a channel as live only after `subscribed`, and refetches what the channel keeps current when it comes back after a gap (`apps/web/lib/stream.ts`).

## 16. Rules for parallel build agents

1. **Own your directory.** Edit only the package/app you were assigned plus your branch's file under `docs/log/`. Never touch root files, `pnpm-workspace.yaml`, `pnpm-lock.yaml`, or another package.
2. **No installs, no new dependencies.** Everything you need is already installed (see the catalog in `pnpm-workspace.yaml`). If something essential is missing, append a line to `docs/NEEDED_DEPS.md` (`package — version — why — who`) and write the smallest local substitute so your package still typechecks.
3. **Check your work**: `pnpm --filter @foundmill/<name> typecheck`, `lint`, `test`. Fix every error in your package before you finish.
4. **No long-running servers on fixed ports** during the build phase (other agents share the machine). If you must boot something, use an ephemeral `PORT=0`/random port and stop it.
5. **Fetch current docs** before using an SDK (Temporal, Claude Agent SDK, Anthropic, Drizzle RLS, Tailwind v4, Storybook 10, react-grid-layout 2, TanStack Table 8, visx, PixiJS 8, xterm 6, Tiptap 3). Versions in the catalog are the truth.
6. **Mock first.** Everything must work with `INTEGRATIONS_MODE=mock` and `MODEL_MODE=mock`. Live paths are implemented but never required for tests.
7. **Design discipline.** UI follows `docs/DESIGN.md`. Tokens only, design-system components (`packages/dugout`) only, Lucide only; the console is desktop only, and the outer product is to work from 390 px (CLAUDE.md "Small screens", not built yet).
8. **Do not commit.** The orchestrating session commits between waves.
9. **Report** at the end: what exists, what is stubbed, commands that pass, and anything another package must know (exported names changed, contracts added).

## 17. Staging deployment notes (Railway + Vercel)

- Every backend service is built from the root `Dockerfile` (one image on `node:22.23.3-bookworm-slim`, the first Node whose corepack runs pnpm 12; `APP` build arg selects the package) and started by tini as PID 1 running `cd apps/<app> && exec node --import tsx src/index.ts` (the image's `ENTRYPOINT`/`CMD`), so the service's own node process receives SIGTERM. Never `pnpm --filter @foundmill/<app> start` in a container: corepack's pnpm shim does not pass SIGTERM on (docs/DEPLOY.md §3 "Redeploys and shutdown"). CI builds the image and boots it to `/health` on every push.

- Internal URLs between services use `http://<service>.railway.internal:<port>` (e.g. `GATEWAY_URL=http://gateway.railway.internal:4001`, `TEMPORAL_ADDRESS=temporal.railway.internal:7233`, `REDIS_URL` from the Railway Redis service).

## 19. Foundations on the first open

A new business gets its vision, first specification and first roadmap when it is first opened (BUILD §11.1, §11.5).

- **What commit starts (WP-04 T3; founder, 2026-11-16 D1 and D4).** A founder whose profile names a budget (`budget_minor` above 0) gets today's start: the archetype's first-cycle tasks and cycle 1 started at commit. A founder with no budget gets `firstCycleTasksFor(seed, { hasBudget: false })` (no finance or legal task; the open-questions task waits `ready`), no cycle at commit (`CommitIdeaResult.cycle` is null), and a spend line of 0 on the Commit screen, so every spend asks first. Their first round is cycle 1 (numbered from history) and starts on the plan's approval (`startBuilding` → `startCycle`), a press of Continue, or the overnight shift's first look; the page and the plan draft on the first open as for everyone.

- **State.** `business_foundations` (migration 0018, one row per business, read-only policy: services write, members read): `pending` at commit → `drafting` (claimed, `attempt` + 1) → `ready` or `failed`. The vision is stored on the row (`vision`); the specification goes to `spec_blocks` and the roadmap to `roadmap_items`, both through `repos.product`. While drafting, `progress` (migration 0019, jsonb on the same row, same policies) holds what has been written so far (`FoundationsProgress`: the vision, the plan's theses and roadmap titles, each finished section, the roadmap items), already plain text with figures labeled; it survives a failed attempt (Try again resumes from it) and `apply` clears it. `repos.foundations` owns the lifecycle: `create`, `claim(from)`, `setRunner`, `writeProgress` (atomic jsonb merge for the current attempt; one section at a time so parallel batches never overwrite each other; its `foundations.progressed` event in the same transaction), `fail`, `inputs`, `author`, `apply`. `apply` and `fail` act only for the current drafting attempt, and `apply` never writes a pinned block or one someone already wrote (the write is conditional on the version it read as empty). The Inbox note and its `inbox.item_created` event (`onInboxItem`) and the `foundations.progressed` "ready" event (`onApplied`) are written in the same transaction.
- **Inputs.** Door A (Ideation Studio): the committed idea (title, summary, archetype, the ten attributes with evidence, citations, Q&A) and the founder profile of the business's creator. Door B (Import): the same plus the Import report snapshotted on the row at commit and the chosen sources commit stored as `sources` (`relevance.import` with `status: "pending"`, only `http(s)` URIs). The sign-up job reads nothing (there is no business, connection or gateway session yet): it checks the typed values and the report words every source still to be read "once …". Commit then starts `importBusiness`, which reads each source with the one read-only gateway call `IMPORT_READERS` (packages/shared) names and records `read` or `failed` with the reason on the row; without a worker the rows are marked not read at once. Product › Sources shows each import source's state, and Read now (`import.readAgain`, owner/admin) reads the ones that were not read again once they are connected. The link is the Import job id, an HMAC-signed token (`SESSION_TOKEN_SECRET` under the label `foundmill/import-job/v1`; a per-process key in development and test) that names the account that started it: `idea.generate({ importJobId })` records it on the idea Import drafts; commit reads it back, verifies it again (signed, this founder, a finished sign-up job with no business, sources that pass the same validation as `import.start`) and rebuilds the job (deterministic in its token).
- **Trigger.** The business shell calls `product.foundations.ensure` on load while `business.get` reports the foundations `pending` or `drafting` (`foundationsStatus`; never once they are ready, failed or absent) (any member; idempotent: one conditional claim, made only by a member with product write, so a viewer opening first leaves it pending; it returns only the status, door, attempt and times). On Temporal each drafting activity heartbeats and passes its cancellation signal to its model calls, so a timed-out attempt stops before the retry. An attempt older than 10 minutes (local) or 45 minutes (Temporal) counts as interrupted and becomes `failed`; the UI stops polling it and offers Try again. `product.foundations.retry` (product write) re-claims a failed one. `product.foundations.get` (product read) returns the state, the vision (while drafting as soon as it is written), the progress (`FoundationsProgressView`: stage, author, each section with its thesis or its text, the roadmap items written and planned) and a summary.
- **Drafting (staged, audit P3).** `packages/agents` foundations-staged (pure) and foundations-steps (calls the client it is given; not re-exported from the package root). Every call shares one system prefix, sent with a cache breakpoint: the house rules and the Product lead's instructions, then the `foundations_brief` prompt with the trusted inputs as JSON (`<`, `>` and backticks escaped). The user turn carries the untrusted inputs (model-written text: the idea card's title, summary and evidence, text already in the outline; research; imported content), each inside `<untrusted_content>`, then, for steps 2 and 3, the plan (model-written, so inside `<untrusted_content kind="plan">`), then the step's instruction. Step 2, `foundations` route, in parallel batches of two (three for a long outline, at most six calls): the named sections (`write_sections`), each stored as it streams; a batch that fails or leaves one out is followed by one call per missing section. ## 20. Date and time formats (Settings › Preferences)

The founder's rule (2026-10-11): every signed-in person chooses how dates and times read, for themselves, in every business and on every signed-in screen. US dates and 12-hour times stay the default and what the signed-out pages show. The patterns of each choice, and the table of them, are in docs/DECISIONS.md ("Date formats a person can choose"). Numbers and money do not change (en-US, each business's own currency).

**Storage and API.** `account_preferences` (migration 0022, one row per account, `user_id` unique, `date_format` in `us | day_first | iso`, `time_format` in `12h | 24h`, RLS `user_id = auth.uid()` for select, insert and update; no delete grant). `repos.preferences.get(db, userId)` (the defaults when there is no row) and `.update(db, userId, { date?, time? })` (upsert of what was given). `founder.preferences.get` / `founder.preferences.update` (§13). The enums are `DATE_FORMAT_PREFERENCES`, `TIME_FORMAT_PREFERENCES`, `DateFormatPrefs` and `DEFAULT_DATE_FORMAT_PREFS` in `@foundmill/shared` (Zod: `DateFormatPrefs`, `DateFormatPreference`, `TimeFormatPreference`). The same row holds the guided layer's state since 0064 (guidance, text size, explainers seen, tours done, the checklist dismissal; §4, §13, §14), read through `founder.preferences.guidance` and mirrored for the first byte in the `fm_text_size` cookie the way the date format is in `fm_date_format`.

**Rendering without a flash or a hydration mismatch.** The browser keeps a copy of the choice in the cookie `fm_date_format` (`<date>.<time>.<owner>`, the owner being the user id, or `dev` under the development sign-in; `lib/date-format.ts`). `getServerDateFormat()` (`apps/web/lib/date-format.server.ts`, React `cache()`d) reads it for the signed-in user and asks `founder.preferences.get` only when it is missing, malformed or someone else's. `DateFormatHost` starts from that value, checks it once against the account, rewrites the cookie whenever what it read or saved differs, and saves changes (`useDatePreferences().save({ date })`: optimistic, rolled back on failure; overlapping saves end on what was stored). Sign-out clears the cookie. The host renders the design system's `DateFormatProvider`.

**The API for call sites** (what the remaining migration uses; `@foundmill/dugout` unless noted):

| Where the date is printed | Use |
| --- | --- |
| A client component (design system, widgets, modules, apps/web) | `const { formatDate, formatDateShort, formatMonthYear, formatTime, formatDateTime, formatRange, formatHourOfDay, formatDateYearParts, prefs } = useFormatters()`. `formatDate(d, "weekdayDate")` takes a form's name or its US pattern (`DATE_FORMATS.weekdayDate`); `formatRange(a, b, { withYear })`. |
| A pure helper or a memo outside React | Take `prefs` (from `useDateFormat()` in the caller) and pass it on: `formatDate(d, "dayMonth", prefs)`, `formatDateTime(d, prefs)`, `formatTime(d, prefs)`, `formatDateShort(d, prefs)`, `formatMonthYear(d, prefs)`, `formatDateRange(a, b, { withYear, prefs })`, `formatHourOfDay(h, prefs)`, `formatDateYearParts(d, prefs)`, or `bindFormatters(prefs)` for all of them. Without `prefs` every helper reads US and 12-hour. |
| A chart or library that takes a date-fns pattern | `datePatternFor("dayMonth", prefs)` (forms: `date`, `dayMonth`, `weekdayDayMonth`, `weekdayDate`, `longDate`, `monthYear`, `time`, `timeSeconds`, `dateTime`, `dayMonthTime`). |
| A server component, or a server-safe design-system component (`SERVER_SAFE_FILES`) | No hooks: take the choice as a prop and call `bindFormatters(prefs)`. The design system's server-safe components that print a date take it as `datePrefs?: DateFormatPrefs | null` (`DevelopmentChart`, `FeedPost`, `ReadReceipt`, `LiveRun`); a client caller passes `datePrefs={useDateFormat()}`, and without it they read US and 12-hour. |
| apps/web's UTC helpers (`apps/web/lib/format.ts`, settings and CRM copy) | `formatDate(v, prefs)`, `formatDayMonth(v, prefs)`, `formatMonthYear(v, { long }, prefs)`, `formatDateTime(v, prefs)` (still UTC, still "UTC" after a time). |
| A test or a story in another format | Wrap it in `<DateFormatProvider value={{ date: "day_first", time: "24h" }}>`. |

Rules for each call site:

1. Replace a literal pattern with the form's name (`formatDate(d, "MMM d")` → `formatDateShort(d)`); never spell a day-first, ISO or 24-hour pattern (the US English guard allows them only in `lib/date-preferences.ts`). A pattern that is not a form (`"yyyy"`, `"EEE"`, `"MMM"`) prints as written in every choice.
2. Leave alone: relative times (`formatRelative`: "3 min ago"), dates written inside agent prose and other stored text, machine formats (day keys such as `2026-10-07`, ISO strings on the wire, a `<time dateTime>` attribute, file exports), and numbers and money.
3. The provider makes the *format* the same on the server and in the browser; it does not make the *time zone* the same (the server renders in UTC). An absolute local time in server-rendered markup renders only once hydrated (`useHydrated()`, `useClientToday()`, `useClientNow()` in `apps/web/lib/today.ts`) or prints in UTC through `apps/web/lib/format.ts`. A date-only string (`2026-10-07`) is read by the design system's helpers as that calendar day wherever the reader is.
4. A memo that formats must list the formatters (or `prefs`) in its dependencies, so a change of choice redraws it without a reload.
5. A component whose dates now follow the choice gets a test in a second format (a provider in its test) and keeps its US story.
