## docs/DECISIONS.md (added after main's last entry)

### 2026-11-13 — The security review of invitations and roles: the calls made

The review of the waitlist-invitations branch (four commits on `79f55143`) had seven findings to fix before production and five cheap ones. All this session's calls.

- **An invitation that names an address is that address's, whatever the role.** The review asked it for every invitation with an email; a collaborator invitation the founder typed an address for is bound too, and only a link-only collaborator invitation works for whoever holds it. Any other account gets the same `invitation_unavailable` as a dead link, so a forwarded link says nothing about who it was for. The address compared is the token's own confirmed `email`, lowercased. A development account's token carries none, so where the dev bootstrap runs (development or test, the bypass on, PGlite) the api compares the stub account's address in `auth.users` (`dev-<id>@foundmill.local`); nowhere else.
- **A cofounder invitation always names an address**, in the api (`invitationNeedsEmail`) and in the database (0091's `invitations_cofounder_email`, `not valid` so it holds for every row written from now on). A link-only cofounder invitation from before 0091 is refused by the api (`workingInvitation`), not migrated.
- **Who may let a new account in.** Only an inviter the list names, the development bypass user, or an account admitted by open sign-up or as `existing`; never one an invitation let in. Such an inviter's invitation still adds an accepter who is already in. **Three new accounts a UTC day per inviter** (`INVITATION_ADMISSIONS_PER_INVITER_PER_DAY`), counted by a query under the same advisory lock as open sign-up's count, taken before either count. When the inviter may not admit (or is past three): under open sign-up the ceiling decides, as it would at sign-in; in invite-only mode the accept is refused (`invitation_cannot_admit`, 403, or `invitation_admissions_limit`, 429), the invitation stays pending and nothing is written.
- **Under open sign-up an invitation's admission counts toward the day's ceiling, and only a trusted inviter's goes past it** (revised Nov 13 after the second review's P2-1; the first version let every eligible inviter past). Every account open sign-up admits is an inviter, so "never stopped by the ceiling" made the real daily cap grow with every day's admissions, and invitations could fill the ceiling and lock ordinary sign-ups out. Now: an inviter the list names, the development bypass user, or a person from before (`existing`) may go past the ceiling (`inviterStanding` "trusted"), within their three a day and within **50 invitation admissions a day past the ceiling for every inviter together** (`INVITATION_ADMISSIONS_PAST_CEILING_PER_DAY`). An inviter open sign-up let in is stopped at the ceiling like any sign-up: the invitee meets the same "You're on the list." words as at sign-in (`on_waitlist`, no email promised) and the invitation stays pending, so the same link works once there is room. The 50 is counted without a column: past the ceiling only invitations admit, so the day's admissions past it are the day's `open` and `invitation` count less the ceiling, read under the same advisory lock, taken before every count (a ceiling lowered during the day only makes it stricter). "Finding people is seamless" still holds for the people the product trusts most; a cofounder asked for by someone who came in through open sign-up waits for the next day's room, which is the cost of a cap that holds.
- **The cutover is a function, not a table.** 0091 stores the moment it ran as the constant of `admission_existing_before()` (service role only). A one-row settings table would have needed RLS, a schema mirror and a test of its own for one value that never changes; SIGNUP_EXISTING_BEFORE overrides it. The api reads it once per database and keeps it.
- **The Team permission, not the role alone** (`mayMakeInvitation`: `rolesThatMayInvite` and `effectivePermission(team) === "write"`), when the invitation is made and whenever it is read or accepted, so narrowing an admin's Team access stops their links at once.
- **An ended collaborator's row gets a new start** when they accept a new invitation (`renewEnded`: the invitation's role and section rules, no end date, `source: "invite"`, the same row and id), rather than a second row or `already`.
- **The invitation page reads from the browser, straight to the api** (not the same-origin `/api/trpc` path, which reaches the api from the web's own addresses). There is no secret the web and the api share, and adding one only to forward a visitor's address would be a deploy change on both services for something the browser already does. The server render no longer asks the api at all.
- **"Don't send me invitations" is a platform-wide suppression**, as asked, so it also stops every project's own mail to that address (`isSuppressed` honors platform scope everywhere). Its page says exactly that ("no invitations, and no email from the projects built here"). The token carries the suppression list's hash of the address, never the address, under its own signing label. `platform_notify`'s `unsubscribeUrl` is required again for every message.
- **The numbers for email to an address:** 10% of PLATFORM_NOTIFY_DAILY_CEILING (`ADDRESS_EMAIL_CEILING_SHARE`, at least one), five emailed invitations a day per inviter (`INVITATION_EMAILS_PER_INVITER_PER_DAY`), three a day per address as before; never the recipient account's own three a day. `invitation_accepted` left `LIMITED_EMAIL_KINDS`: it answers what the inviter did.
- **0092 closes a collaborator's reads of twelve tables and the invitations**: the admin-written Money, Legal and Settings tables and the Money tables services write (accounts, securities, cap table, usage ledger, credit balances, checkouts, legal entities, incorporations, integrations, webhooks, policies, App installations). Left readable, each because a collaborator's own screens read it: departments and their members (the Team), vacation periods (the shell), the logo and the foundations (shell and Home), product research (Product), session recordings (Live sessions), contact consents (Customers), sample rows. **Not closed:** the Money and Legal tables members write (transactions, ledger snapshots, forecasts, filings, contracts, compliance events, regulatory gates): a collaborator still reads and writes them in the database as a member, and only the api keeps them out. Closing them means changing their write policies too, which is more than this change. Named in `rls/people-roles.test.ts`, ARCHITECTURE and 0092's header. Two effects of the closure in the api: the approval pane no longer says whether GitHub is connected to a collaborator (null, as for a call that is not GitHub's), and an agent's wage on its profile reads 0 to a collaborator (the usage ledger is closed to them).
- **0090's header was edited in place** (a comment only): 0090 is not on main, the migrator checks no hashes, and the sentence was false.
- **The waitlist line promises no email** until the waitlist that sends it exists: "You're on the list. We'll let you in as soon as there is room. Come back tomorrow to check." The email sentence is kept as `ON_WAITLIST_EMAIL_PROMISE` for the change that ships the waitlist.
- **The races are tested on PGlite for their mechanism** (one connection: two accepts, or an accept and a revoke, run one after the other): exactly one wins, and the conditional UPDATE answers null once the row is not pending; the lock is shown to be taken before the per-inviter count. Each such test says it needs a real-Postgres run.
- **Recorded, not fixed today:** one person can still use the open-mode ceiling with many addresses (per-domain caps and a captcha belong before open sign-up is switched on); tokens travel in GET query strings (`invitation.byToken`, the off links); apps/stream and apps/collab do not check that the address is confirmed; a single cofounder can remove the founder who created the project and request its deletion, and the other founders are not told.

### 2026-11-13 — The second review of invitations, and the Money and Legal tables: the calls made

The second security review of the waitlist-invitations branch had no P1s and five follow-ups; the coordinating session added a hard line on the Money and Legal tables. All this session's calls, except the line itself.

- **0093 is its own migration, not folded into 0092.** 0092 is not on main, but a database that already ran it (a development stack, a staging try) would never get an edit to it, the same reason 0088 replaced 0087's guard. 0092's header only gains a pointer (a comment).
- **The write policy is `has_role(owner/admin/member) and is_member_not_collaborator`, not a new function.** A person has one membership row per business, so the conjunction is exactly "a writer's role that is not a collaborator's", and the writers stay what `fm_tenant_table` gave them (an owner, so a cofounder, an admin, a member). The FOR ALL policy had to change as well as the select one: it answers SELECT too, so closing `T_select` alone would have left the rows readable.
- **The migration refuses to run when one of the seven carries any other policy**, so a policy added later is a decision for whoever adds it. The test reads every policy on the seven and on the 0092 tables.
- **No api change was needed.** Every Money and Legal procedure is `sectionRead`/`sectionWrite` on Finance or Legal, which a collaborator never holds; the Home sentences (`business.areas.words`), the metrics and a revenue goal wall themselves already; nothing a collaborator can call writes these tables on their connection. A viewer and an advisor keep reading them, as before.
- **The /64 is applied in `callerLimitKey`, for every per-caller window,** not only the invitation read: the public project and person pages, the Follow form and the milestone cards had the same weakness and share the key function.
- **A local helper in @foundmill/shared, with a TODO.** PR #98's `limitAddress` is inside apps/api's idea box and not on main; this one gives the same output so whichever merges second deletes the other.
- **60 reads a minute per token, keyed by the token's hash**, taken in the same take as the ceiling for all (both or neither) and given back with it when the token names nothing, so a guess never fills a window. A token of the wrong shape is never looked up and gets no window.
- **The past-ceiling cap is counted, not stored.** Past the ceiling only invitations admit, so the day's admissions past it are the day's count less the ceiling (see the revised entry on open sign-up above).
- **The wrong account is told what to do, which says the link is addressed.** "Sign in with the address this invitation was sent to." (`invitation_other_address`, 403) replaces the dead-link words for an addressed invitation met by another account, as the review asked; the address and nothing beyond the page's own preview is shown. A dead link keeps `invitation_unavailable`. This reverses the first review's call that both read the same.
- **Decline of an addressed invitation is refused, not answered "ok", when the caller is not its address** (signed out included). An "ok" that did nothing would have shown "Invitation declined" to someone whose decline did not happen. A dead link still answers ok to anyone; a link-only invitation is still the token holder's to decline.
- **The inviter's row is locked `for share` only in the accept's transaction**, the one place a later demotion must wait for; the reads outside a transaction stay plain.
- **Left for the next task (P2-3):** telling every founder when one of them demotes or removes another, or asks for the project's deletion.
